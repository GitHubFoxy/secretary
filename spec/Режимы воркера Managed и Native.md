# Secretary V2 — Режимы воркера: Managed и Native

> **Статус:** принятый подход. Заменяет прежнюю идею «отслеживать сообщения пользователя в сессии воркера» (см. §8).
> **Связано:** [[THE spec]] (раздел «Перехват Workerа»), [[memory]] (источник истины в БД сервера).
> **Харнессы в охвате:** Claude Code и Codex. FX, Pi, OpenCode позже.

## 1. Идея

У сессии харнесса должен быть **ровно один владелец** в каждый момент. Поэтому у воркера два взаимоисключающих режима, и пользователь переключает их явно кнопкой **«Open in native harness»**.

| Режим | Кто держит процесс | Кто может писать | Что видит пользователь |
|---|---|---|---|
| **Managed** | Сервер, через SDK (Claude Code) или `codex app-server` (Codex) | Secretary и упрощённый интерфейс воркера | Структурный интерфейс: сообщения, вызовы инструментов, кнопки разрешений |
| **Native** | Узел, родной TUI (`claude` / `codex`) в PTY | Только пользователь в терминале | Настоящий харнесс со всеми функциями (rewind, слэш-команды и т. д.) |

Пока воркер в Native, упрощённый интерфейс этого воркера доступен только для чтения, а сообщения от Secretary не принимаются. Так к журналу сессии в любой момент подключён один процесс, и два рассинхронизированных клиента невозможны.

Это же решает прежнюю проблему рассинхрона между Secretary и Worker: **факт входа в Native уже является сигналом «пользователь мог что-то изменить»**. Определять отдельные сообщения пользователя не нужно.

## 2. Переходы

```text
            «Open in native harness»
Managed ───────────────────────────────▶ Native
   ▲   1. дождаться конца хода (или прервать по решению пользователя)
   │   2. остановить управляемый процесс
   │   3. взять блокировку (lease), запустить TUI с resume в PTY
   │
   │   выход из TUI / кнопка «Вернуть» / истёк таймаут бездействия
   │   1. освободить блокировку
   │   2. needs_sync = true
   │   3. синхронизация (§4)
   └── 4. запустить управляемый процесс с resume
```

## 3. Блокировка

- Блокировка хранится на сервере как **аренда (lease) с heartbeat от узла**, а не как флаг. После падения узла аренда истекает сама, воркер не остаётся закрытым навсегда.
- Пока аренда активна, сервер отклоняет любую отправку воркеру из Managed-каналов.
- Выход из Native: завершение процесса TUI, кнопка «Вернуть» или таймаут бездействия (настраиваемый, по умолчанию выключен либо большой).
- Переключение в Native во время хода, фоновых задач или субагентов требует явного решения пользователя: подождать или прервать. Интерфейс показывает, что именно будет прервано.
- Для удалённых воркеров PTY и блокировка живут на узле воркера. Пользователь подключается через встроенный терминал.

## 4. Синхронизация при выходе из Native

Запускается сразу при выходе (ждать паузы не нужно).

1. Сервер фиксирует границу: события воркера после `last_synced_seq` до момента выхода.
2. Суммаризатор получает **только дельту** плюс предыдущую записку, а не весь тред.
3. Узел добавляет факты из среды отдельным блоком (для кода: ветка, коммиты, размер диффа, состояние дерева, результат тестов).
4. Записка сохраняется как событие `worker_sync` со ссылками на исходные события.
5. `needs_sync = false`, воркер возвращается в Managed.

Правила для общего чата:
- Сообщение пользователя в общий чат **принимается сразу** и ставится в очередь по порядку. Пользователь видит `sync in progress` и может писать дальше.
- Пока идёт синхронизация, **обработка всех сообщений приостановлена** (решение: чтобы у Secretary было понимание, что происходит). После синхронизации очередь обрабатывается по порядку.
- Если суммаризатор упал, `needs_sync` остаётся, Secretary явно говорит об этом и не выдумывает состояние. Повтор с ограничением попыток.
- Суммаризатор не получает прав менять память или навыки. Содержимое транскрипта для него данные, не инструкции.

## 5. Сообщения Secretary к воркеру в Native

Secretary получает немедленный ответ «воркер открыт пользователем в родном харнессе» и сообщает об этом пользователю. Сообщение молча не теряется. Ставить ли его в очередь автоматически, решить отдельно (§6).

## 6. Открытые вопросы и что проверить

1. **Совместимость resume (не проверено).** Сессия, начатая через SDK или app-server, открывается в родном TUI с тем же журналом и тем же идентификатором, и наоборот. Особенно что `resume` не создаёт новую сессию и не разветвляет журнал. Проверить на установленных версиях Claude Code и Codex.
2. **Очередь для Secretary:** ставить ли сообщения Secretary к воркеру в очередь на время Native или только отвечать «занято».
3. **Таймаут бездействия** в Native: нужен ли и каким по умолчанию.
4. **Какой суммаризатор** (модель, откуда подписка или токен) и где он запускается.
5. **Что считать событием воркера** в транскрипте, чтобы дельта не включала служебный шум (повторы, сжатие контекста, внутренние сообщения харнесса).
6. **Правка в Native, которая меняет журнал без хода агента** (например, rewind): как отразить это в дельте.

## 7. Приёмочные тесты

- Во время Native сервер отклоняет сообщение воркеру из упрощённого интерфейса и от Secretary, и сообщает причину.
- В любой момент к журналу сессии подключён не больше одного процесса харнесса.
- Вход в Native ставит `needs_sync`, выход запускает синхронизацию.
- Падение узла в Native: аренда истекает, воркер возвращается к доступному состоянию без ручного вмешательства.
- Переключение в Native во время хода или фоновой задачи не происходит без явного решения пользователя.
- Сообщение пользователя в общий чат во время синхронизации принимается сразу, обрабатывается после неё и в правильном порядке. Несколько сообщений не теряются.
- Суммаризатор получает дельту и предыдущую записку, а не весь тред.
- Записка содержит факты из git отдельным блоком, и они совпадают с реальным состоянием репозитория.
- При сбое суммаризатора Secretary говорит об этом явно и не выдумывает результат.
- Повторная доставка или перезапуск сервера посередине перехода не дублируют события и не теряют блокировку.
- Текст в транскрипте вида «игнорируй предыдущие инструкции» не меняет поведение суммаризатора.
- После `worker_sync` вопрос о недавней ручной работе в воркере получает ответ из записки, а не из догадки Secretary.
- Сессия, созданная в Managed, открывается в Native с тем же журналом, и наоборот (по результатам проверки §6.1).

## 8. Прежний подход (отклонён), коротко

Идея была такая: оставить два клиента на одной сессии (терминал и упрощённый интерфейс) и **отслеживать**, когда пользователь написал воркеру напрямую.
- Каждый вход получал `origin` (`secretary`, `user_ui`, `user_terminal`), любое сообщение не от Secretary ставило воркеру `needs_sync`.
- Фоновая синхронизация запускалась после паузы, суммаризатор читал дельту, узел добавлял факты из git.
- Проблема: два клиента на одной сессии конфликтуют (два процесса на одном журнале, либо вставка текста в PTY, которая хрупка при незавершённом вводе, меню и диалогах разрешений). Заметка была бы нужна только для лечения последствий этой схемы.
- Новый подход убирает причину, а не лечит последствия: владелец сессии всегда один.

## 9. Как у T3 Code

T3 Code обошёл проблему иначе: сервер единственный владелец процесса (Claude Code через Agent SDK, Codex через app-server), а терминал в нём отдельный shell, а не TUI агента. Родного TUI с его функциями у T3 нет. Режим Native из этой заметки возвращает именно то, чего T3 лишён. Источник: `pingdotgg/t3code`, `apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts` и `CodexAdapterV2.ts`, `docs/user/terminal.md`. Вывод про терминал сделан по документации, код терминала не читался.
