## Executive Summary & Архитектурный разбор для Secretary v2

### 1. Критика Feature-Sliced Design (FSD) в продуктовой разработке
Дмитрий подробно разбирает проблемы, с которыми сталкиваются команды при масштабировании FSD в реальных проектах:
- **Жесткая вертикальная иерархия слоев** (`app` -> `processes` -> `pages` -> `widgets` -> `features` -> `entities` -> `shared`). Правило "слой выше может импортировать только слои ниже" отлично звучит в теории, но на практике приводит к коллизиям.
- **Огромный навигационный оверхед в IDE:** Чтобы разработать или изменить одну пользовательскую фичу, разработчику приходится прыгать между 4–6 папками на разных уровнях дерева (`entities/user`, `features/user-avatar`, `widgets/user-profile-card`, `pages/profile`). По подсчетам спикера, это отнимает до часа в день на чистую навигацию по файловой структуре.
- **Размытая грань между `entities` и `features`:** Разработчики тратят часы на споры, где заканчивается "сущность" и начинается "фича" (например, отображение баланса пользователя с кнопкой обновления).
- **Циклические зависимости и обход правил:** Когда двум фичам или сущностям нужен общий код, разработчики либо искусственно выносят всё в `shared` (превращая его в свалку "God-object"), либо создают костыльные промежуточные виджеты.
- **Несоответствие реактивным и fullstack-фреймворкам:** Классический Clean Architecture / FSD перегружен бэкенд-специфичными слоями (репозитории, DTO, адаптеры), которые в реактивном фронтенде (Svelte / SvelteKit / React) избыточны и лишь увеличивают бойлерплейт.

### 2. Концепция FDA (Фрактально-Доменная Архитектура)
FDA предлагает отказаться от глобальной слоистой пирамиды в пользу **модульно-доменной декомпозиции с фрактальной структурой**:

```
src/ (или web/src/)
├── domains/
│   ├── tasks/                  # Домен: задачи и воркеры
│   │   ├── index.ts            # Public API домена
│   │   ├── ui/                 # Компоненты домена
│   │   ├── model/              # Стейт / реактивные хранилища
│   │   ├── api/                # Транспорт (REST / WebSocket / RPC)
│   │   └── subdomains/         # Фрактальная вложенность при росте сложности
│   │       └── execution-node/ # Поддомен: ноды выполнения
│   │           ├── ui/
│   │           └── model/
│   ├── chat/                   # Домен: диалоговая сессия
│   │   ├── index.ts
│   │   ├── ui/
│   │   └── model/
│   └── memory/                 # Домен: долговременная память
└── shared/                     # Базовые UI-примитивы (кнопки, модалки, утилиты)
```

#### Ключевые принципы FDA:
1. **Бизнес-домены на первом уровне:** Структура проекта отражает бизнес-логику и понятна не только разработчикам, но и продуктовым менеджерам (например, `tasks`, `chat`, `nodes`, `settings`).
2. **Инкапсуляция и Public API (`index.ts`):** Каждый домен предоставляет наружу только то, что необходимо другим доменам. Внутренности домена приватны.
3. **Функциональные слои внутри домена:** Внутри домена код делится на функциональные части (`ui`, `model`, `api`, `lib`), при этом количество слоев адаптируется: простой домен может содержать всего 2 файла, сложный — полноценную подсистему.
4. **Фрактальность (самоподобие):** Если домен разрастается, он не ломает глобальную архитектуру, а дробится внутри себя на поддомены (`subdomains/`), повторяющие ту же структуру.
5. **Fullstack Monorepo Friendly:** Отлично работает в монолитах и meta-фреймворках (SvelteKit, Next.js, Go + Svelte embedded), где один разработчик держит в фокусе сквозной сценарий.

---

### 3. Применимость к Secretary v2
- **Архитектура `web/` (Svelte Control Room):**
  - Вместо раздувания FSD-слоев (`widgets/`, `features/`, `entities/`), клиентская часть Secretary v2 структурируется по доменам FDA:
    - `domains/tasks` (жизненный цикл Task, Attempt, Result, Queue).
    - `domains/chat` (интерактивный диалог, стриминг ответов).
    - `domains/nodes` (статус подключенных `secretary-node` хостов).
    - `domains/approvals` (Human-in-the-loop подтверждения опасных действий воркеров).
- **Синхронизация с бэкендом Go (`internal/`):**
  - Доменная структура фронтенда зеркалирует пакеты ядра Go (`internal/core`, `internal/ctl`, `internal/node`), обеспечивая ментальную согласованность для fullstack-разработки.
