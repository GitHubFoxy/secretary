# Secretary Node menu bar companion

On macOS 13+, the normal `secretary setup` flow builds and installs a signed, Spotlight-discoverable **Secretary Node.app** in `~/Applications`. Upgrades run the same installer and replace the bundle without touching the OS Launch at Login preference. You can also run `bash macos/SecretaryNode/install.sh` from a configured checkout. Xcode command-line tools (Swift) and `codesign` are required. The signing step uses local ad-hoc signing for self-hosted installations; distributing a notarized binary requires a separate Developer ID release process.

Use Spotlight to open **Secretary Node**. This is a menu bar-only app with native system light/dark appearance. It owns a single managed Node, using the existing `~/.local/bin/secretary-node` executable and `~/.local/share/secretary/node/config.json`; optional `SECRETARY_NODE_EXECUTABLE` and `SECRETARY_NODE_CONFIG` overrides are preserved. Do not install the legacy `secretary node install-service` LaunchAgent alongside the app. If that service exists, run `secretary node uninstall-service` before installing the app. The installer refuses to proceed while that service is installed or loaded.

The menu shows Node, Server, a separator, discovered harnesses, **Launch at Login**, **Open Logs**, and **Quit Secretary Node**. Launch at Login uses the macOS ServiceManagement setting and persists across relaunch and app upgrades. Quit gracefully stops the verified managed Node before exiting; reopening from Spotlight starts or recovers the managed Node. The log at `~/Library/Logs/SecretaryNode/node.log` captures managed Node stdout/stderr across restarts. Open Logs opens that file in the default registered app, or displays an actionable error when missing or inaccessible. The app does not adopt arbitrary external Node processes, manage the Server, or silently stop unrelated services.

CI smoke: `swift test --package-path macos/SecretaryNode` and `bash macos/SecretaryNode/install.sh` (with a configured Node binary). The macOS workflow exercises fresh install, replacement upgrade, bundle signature and conflict rejection. Manual checks: Spotlight indexing and relaunch; actual login/logout login item enable/disable and upgrade persistence; native dark/light appearance and menu layout; live Node start/stop and reopened log content; behavior with a real configured Server and harness.

CI lifecycle tests validate managed Node start/stop, recovery across companion controller replacement, and prevention of duplicate managed processes. They do not register a real macOS login item inside a graphical user session. Manual acceptance must toggle Launch at Login in the installed signed app, approve it in System Settings if requested, verify persistence after app restart and reinstall, and verify a single Node after macOS logout/login. When ServiceManagement reports approval required or missing app registration, the menu provides system-settings or installation guidance. If a log exists but cannot be read, Open Logs reports an access error instead of treating it as missing.

## First enrollment and independent status

The combined Mac installation reads the first-enrollment credential from the private `~/.local/share/secretary/environment` created by `secretary setup`. Only the Node pairing credential is passed to the managed Node. The Node itself persists its identity in the configured `data_dir/identity.json`; subsequent app launches reuse that identity without importing the pairing token. The standalone installation retains its own explicit enrollment workflow and configuration. Incomplete or unreadable combined-install pairing setup is shown as an actionable Node startup failure: rerun `secretary setup` and reopen the app. The menu does not print the token.

The Server row uses an independent unauthenticated HTTP `GET /v1/health` check against the configured Server URL. It reports Checking, Online, Offline, or Unavailable (with setup guidance when the Server URL cannot be read), regardless of Node process failures; Node connection and harness rows use the Node status snapshot only. Online means HTTP health answered successfully, not that Node enrollment, heartbeat, inventory, or Worker dispatch succeeded.

Automated regressions: `swift test --package-path macos/SecretaryNode`, including `NodeAppConfigurationTests` and `ServerHealthMonitorTests`, runs in the `macOS Node App` PR workflow on `macos-15`. Real acceptance remains manual: install the official package in a clean macOS account; complete interactive setup; start the Server; open the installed app; verify exactly one paired Node, heartbeat and inventory; quit/restart the app and compare the persisted Node identity; then simulate a Node exit while Server health remains OK and inspect the independent menu rows and private Node log.

The shell-based lifecycle fixture verifies the app's credential handoff before and after a synthetic identity file appears; it is not a real Node enrollment test and cannot establish registration reuse with Secretary server. The child-environment regression launches an actual shell process and checks that removed inherited secrets never reappear in that process. Real `secretary-node` enrollment, heartbeat, inventory, persisted identity and server-side registration reuse, standalone enrollment, and absence of secret leakage in live logs are **MANUAL** acceptance criteria.
