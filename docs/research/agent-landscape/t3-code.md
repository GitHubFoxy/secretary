# T3 Code: продуктовый отчёт

**Проверено: 5 октября 2026 года.** Это кабинетное исследование по первичным источникам; T3 Code не устанавливался и не тестировался вручную. Для текущего стабильного канала и Nightly проверены GitHub Releases и теги. Документация `main` уже описывает Orchestrator V2, но на дату проверки V2 опубликован как Nightly, поэтому его возможности ниже помечены отдельно от стабильной версии.

> **TL;DR — главное обещание:** T3 Code собирает локальные coding-agent harnesses в одну открытую control surface: несколько агентов и репозиториев, отдельные Git worktrees, диффы и PR — с управлением из desktop, браузера или телефона. Вы платите выбранным поставщикам моделей, а T3 Code управляет их агентами. Это сильная среда для параллельной разработки, но не универсальный личный ассистент и не Secretary с общей Personal Conversation.

## 1. Категория и масштаб

T3 Code называет себя **agent harness control surface**: приложение само не является моделью или основным coding-agent harness, а запускает и объединяет локальные инструменты вроде Claude Code и Codex. Сервер T3 Code владеет проектами, provider-процессами, терминалами, Git-операциями и историей; клиенты показывают их состояние и передают действия на сервер. Репозиторий открыт под MIT. В официальном README команда предупреждает, что проект очень ранний и возможны ошибки. На GitHub во время проверки было около 24,6 тыс. звёзд; заявление сайта о 400 тыс. пользователей — маркетинговое, методика подсчёта не опубликована. [README и архитектурная схема](https://github.com/pingdotgg/t3code), [архитектура](https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md).

Публичный Nightly существует: это не предположение по наличию слова в документации. GitHub помечает его как prerelease, а установка CLI предусматривает канал `nightly`.

Помечен prerelease. | Последняя сборка V2 на дату проверки. Выпуск 2632 после него содержит исправления зависших runs, расчёта стоимости Codex и другие изменения. |

**Как получить и обновлять.** CLI ставится официальным скриптом; `T3CODE_CHANNEL=nightly` выбирает Nightly, `T3CODE_VERSION` закрепляет версию, а `t3 update --channel nightly` переключает установленный серверный CLI. Desktop-сборки доступны в [GitHub Releases](https://github.com/pingdotgg/t3code/releases), nightly-пакет Arch — `t3code-nightly-bin`. Для Nightly V2 требуется обновить и сервер, и подключённые desktop/web/mobile-клиенты: протокол V1/V2 несовместим. На дату проверки мобильные версии из App Store и Google Play ещё были V1; V2 распространялся через TestFlight и Android beta. [Установка и каналы](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md), [инструкция по миграции V2](https://github.com/pingdotgg/t3code/issues/14871).

Nightly — prerelease; V2 ещё переводит существующую базу и мобильные клиенты на новый протокол. Официальный issue обещает вести там переход до stable, но даты stable-релиза нет. При первом запуске V2 копирует базу V1; переносит беседы, настройки, проекты, ветки и поддерживаемые вложения, но не восстанавливает живую provider-сессию, старые checkpoints/diffs, tool activity и историю approvals. Следующее сообщение в старой беседе начинает новую сессию и передаёт ей ограниченный контекст. Перед обновлением важного проекта это существенный риск, даже при сохранённом тексте истории. [Migration notes](https://github.com/pingdotgg/t3code/blob/main/docs/user/thread-migration.md).

### Что добавляет Nightly V2

Первый V2 Nightly перестраивает запуск, остановку, очередь и возобновление агентов. В нём заявлены Pi, OpenCode 2, ACP Registry agents, `delegate_task` для запуска дочерних агентов на других провайдерах/моделях, видимые subagent threads, форки и возврат контекста, смена провайдера посреди беседы, MCP-инструменты T3 Code для управления threads, серверная очередь, возобновление прерванных threads после рестарта, автоматический resume после сброса лимита и scheduled tasks. Последний Nightly 2632 добавил, среди прочего, отображение расходов по типу токенов/скорости/модели и пробуждение агента при изменении checks, review или конфликтов PR. Это возможности Nightly, не обещание текущего Stable. [V2 release notes](https://github.com/pingdotgg/t3code/releases/tag/v0.0.46-nightly.20261003.2610), [последний Nightly](https://github.com/pingdotgg/t3code/releases/tag/v0.0.46-nightly.20261003.2632).

## 3. Установка и первый полезный сценарий

Сначала на машине, где будут лежать файлы и запускаться агенты, устанавливают и авторизуют хотя бы один provider. Затем ставят desktop-клиент либо CLI и запускают `t3`; CLI поднимает сервер и открывает web-клиент. Для первого рабочего цикла пользователь подключает Git-репозиторий, выбирает provider и режим разрешений, создаёт thread с задачей, а затем смотрит изменения, проверяет diff и при необходимости создаёт commit/PR. Это реконструкция по официальным инструкциям, не замер времени onboarding. [Install](https://github.com/pingdotgg/t3code/blob/main/docs/user/install.md), [работа с threads](https://github.com/pingdotgg/t3code/blob/main/docs/user/thread-sidebar.md), [Source Control](https://github.com/pingdotgg/t3code/blob/main/docs/user/source-control.md).

У каждого thread может быть отдельная ветка и изолированный Git worktree; можно выбрать текущий checkout, повторно использовать существующий worktree или создать новый. Есть и thread без проекта: он работает в отдельном scratch-каталоге, но без Git-диффа и branch-контролов. Важное начало безопасного сценария — вручную выбрать **Supervised**: новый thread по умолчанию создаётся в **Full access**. [Permission modes](https://github.com/pingdotgg/t3code/blob/main/docs/user/permission-modes.md), [Working with threads](https://github.com/pingdotgg/t3code/blob/main/docs/user/thread-sidebar.md).

## 4. Harnesses, модели и стоимость

**В Stable README перечисляет:** Codex, Claude Code, Cursor, Grok Build, OpenCode и Google Antigravity. T3 Code запускает их собственные CLI/агенты, а вход и доступ к моделям обычно настраиваются средствами соответствующего provider. Например, документация описывает вход в Codex через ChatGPT-план или существующий Codex CLI login, Claude через `claude auth login`, а Antigravity — через Google account, Gemini API key или поддерживаемые варианты Vertex/Gemini Enterprise. Сам список доступных моделей и лимитов контролирует провайдер. [README](https://github.com/pingdotgg/t3code), [Codex](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-codex.md), [Claude](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-claude.md), [Antigravity](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-antigravity.md).

**Nightly V2 расширяет выбор:** Pi, OpenCode 2 и агенты ACP Registry (например, Devin, Cline, Kimi, Droid) подключаются как providers. Они исполняются на выбранной T3 Code environment, используют собственные инструменты, вход и модельный доступ. В V2 можно сменить provider/model между turns, но смена harness переносит только отобранную часть текста: reasoning, tool calls/results и вложения старого provider могут не перейти. Для сочетания harnesses релиз рекомендует `delegate_task`, а не простую смену provider. [ACP Registry](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-acp.md), [Pi](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-pi.md), [ограничения provider switch](https://github.com/pingdotgg/t3code/releases/tag/v0.0.46-nightly.20261003.2610).

Таким образом, T3 Code — **control surface, а не harness или модель**. Лицензия MIT и отсутствие платы T3 Tools за продукт подтверждены README/Terms; пользователю остаются расходы на подписки, API и хост-машины выбранных providers. Отдельная подписка T3 Code по Terms на дату проверки не взимается, если для функции явно не установлена плата. Usage-панель показывает токены и оценочную API-эквивалентную стоимость; сама документация предупреждает, что это не счёт provider и часть истории может отсутствовать. [Terms](https://t3.codes/terms-of-service), [Usage](https://github.com/pingdotgg/t3code/blob/main/docs/user/usage.md).

## 5. Threads, проекты, изменения и делегирование

Основной durable-объект — **coding thread**, в котором связаны сообщения, activity, выбранная provider-сессия и состояние workspace. Проекты — локальные workspace roots; один проект может иметь threads в разных ветках и worktrees. Видны файловые изменения и diff, есть checkpoints/откат там, где provider это поддерживает, Git-действия, коммиты, push и PR. Source-control интеграции документированы для GitHub, GitLab, Bitbucket и Azure DevOps; часть review/merge-функций зависит от хостинга. Вложенные файлы и изображения доступны агенту через environment. Это не отдельный универсальный реестр артефактов с собственным Task lifecycle: артефакты представлены файлами, диффами, терминальными/preview-результатами и PR в рамках thread. [Glossary](https://github.com/pingdotgg/t3code/blob/main/docs/internals/glossary.md), [Source Control](https://github.com/pingdotgg/t3code/blob/main/docs/user/source-control.md), [Composer](https://github.com/pingdotgg/t3code/blob/main/docs/user/composer.md).

В V2 каждый делегированный child — отдельный thread с provider-native history; его можно видеть в lineage, следить за ходом работы и получить результат. Агент через T3 Code MCP может создавать, запускать, адресовать, ждать, читать, искать и прерывать threads. Это сильный multi-agent механизм, особенно для Claude-планирования и Codex-реализации, но он пока Nightly. T3 сохраняет child-thread как адресуемую беседу; при этом нет отдельной server-owned сущности Worker, привязанной к Task с lifecycle Secretary. [V2 release](https://github.com/pingdotgg/t3code/releases/tag/v0.0.46-nightly.20261003.2610).

Threads можно закреплять, архивировать, усыплять и продолжать. Опция **Continue threads after restarts** выключена по умолчанию; её нужно включить, а сервер на машине всё равно должен снова запуститься. Возобновление зависит от сохранённого состояния provider; терминальные команды могут оборваться. V2 отдельно умеет продолжать поддерживаемые прерванные threads. Следовательно, T3 хранит durable историю и в подходящих случаях runtime-продолжение, но это не универсальная гарантия восстановления любого агента или фонового процесса. [Updating](https://github.com/pingdotgg/t3code/blob/main/docs/user/updating.md), [background service](https://github.com/pingdotgg/t3code/blob/main/docs/user/background-service.md).

## 6. Desktop, web, mobile и удалённое исполнение

Есть Electron desktop, web-клиент и приложения iOS/Android. Мобильный клиент управляет сервером и agent-процессами на другой машине — телефон сам не становится местом исполнения. Несколько подключённых environments можно видеть в общих интерфейсах; каждый thread выполняется в environment, где доступен проект. Для подключения используют локальную сеть/Tailscale и pairing либо T3 Connect. [README](https://github.com/pingdotgg/t3code), [Remote access](https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md).

**T3 Connect — не облачный агент-хостинг.** Он помогает обнаружить машину и установить защищённое соединение без port forwarding; сам host должен оставаться включённым и доступным. Для постоянного доступа CLI может работать как сервис на macOS/Linux; сервис Windows не поддерживается. В обычном режиме после соединения клиент и выбранная environment обмениваются API/WebSocket напрямую, а relay T3 не проксирует обычный трафик. Relay всё же ведёт cloud-учёт связок окружений и устройств и может доставлять уведомления/Live Activities. Можно использовать собственную VM как host, но T3 не обещает бесплатно выполнять код в своей облачной среде. [Remote access](https://github.com/pingdotgg/t3code/blob/main/docs/user/remote-access.md), [Relay architecture](https://github.com/pingdotgg/t3code/blob/main/infra/relay/README.md).

## 7. Разрешения и безопасность

T3 предлагает **Supervised**, **Auto-accept edits**, **Auto** и **Full access**. В Supervised команды и изменения файлов требуют подтверждения; в Full access агент работает без таких подтверждений. Механизм зависит от provider: например, OpenCode не имеет AI-review для Auto и фактически спрашивает как Supervised. Режимы действуют на инструментальные запросы, но это не документированная OS sandbox или изоляция процесса. Поскольку provider запускается на серверной машине, Full access может дать ему права текущего пользователя на файлы и команды. [Permission modes](https://github.com/pingdotgg/t3code/blob/main/docs/user/permission-modes.md), [архитектура](https://github.com/pingdotgg/t3code/blob/main/docs/internals/overview.md).

Удалённый доступ использует pairing, отзыв сессий и scope-based разрешения; соединение с relay и авторизация в environment — разные trust boundaries. Это полезная дисциплина для управления доступом, но она не заменяет sandbox агенту. До использования на чувствительном репозитории нужно проверить provider permissions, доступ конкретной environment и поведение собственных ACP agents; документация прямо отмечает, что registry agents — сторонний код. Независимый аудит эффективности этих границ в рамках исследования не проводился. [Environment authentication](https://github.com/pingdotgg/t3code/blob/main/docs/internals/environment-auth.md), [ACP Registry](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-acp.md), [Security Policy](https://t3.codes/security-policy).

## 8. Приватность, хранение и экспорт

По умолчанию сервер, workspace, provider credentials и thread history находятся на машине, которая исполняет работу; в стандартном каталоге данные T3 лежат в `~/.t3/userdata`. Промпты, исходники и ответы получают выбранные coding-agent/AI-провайдеры согласно их собственным правилам. Relay не является обычным прокси для содержимого сессии, но T3 Connect обрабатывает account/environment/device metadata; для уведомлений может видеть project/thread title, model, status и activity headline. [Архитектура relay](https://github.com/pingdotgg/t3code/blob/main/infra/relay/README.md), [Privacy Policy](https://t3.codes/privacy-policy).

**Телеметрия: в первичных источниках есть конфликт.** Текущая документация репозитория говорит, что сервер отправляет в PostHog product usage events с hashed account/installation ID, provider/model, permission mode, итогом и длительностью turn и доступными token totals; в ней указан отказ через `T3CODE_TELEMETRY_ENABLED=false`. Документация утверждает, что prompts, ответы, содержимое файлов, auth tokens и conversation IDs не передаются в этих событиях. При этом маркетинговая страница обещает «No telemetry unless you opt in». Какое поведение включено по умолчанию именно в бинарниках Stable/Nightly и почему формулировки расходятся — не удалось установить; это нужно проверить отдельно. [Telemetry docs](https://github.com/pingdotgg/t3code/blob/main/docs/user/telemetry.md), [сайт](https://t3.codes/).

Privacy Policy перечисляет account/device сведения, диагностические события и ограниченные данные уведомлений; diagnostic traces настроены на удаление через 30 дней, а для остальных записей формулировка — пока активна учётная запись/функция и столько, сколько разумно требуется для сервиса, безопасности и закона. Запрос на удаление T3 account и связанной T3 Connect data направляется на `privacy@t3.tools`; он не удалит локальные данные environments или историю у provider. Полного экспорта одного thread сейчас нет: документация советует остановить сервер и скопировать `userdata` в безопасное место. Срок удаления копий пользовательских данных и экспортируемый формат полной истории публично не определены. [Privacy Policy](https://t3.codes/privacy-policy), [migration/export notes](https://github.com/pingdotgg/t3code/blob/main/docs/user/thread-migration.md).

## 9. Сопоставление с Secretary

| Примитив Secretary | Что есть у T3 Code | Вывод для Secretary |
|---|---|---|
| **Одна durable Personal Conversation** для разных каналов | Durable coding threads и клиенты web/desktop/mobile; каждый thread привязан к работе и workspace. Telegram/Slack/Discord как каналы одной беседы не документированы. | Сильный образец task-scoped coding thread, не общий личный inbox.
| **Редактируемый базовый контекст пользователя (`user.md`)** | Нет документированного общего контекста личности для всех harnesses. Используются provider-native context/skills и project instructions; V2 добавляет Pi с его обычными context files. | Не считать provider configs заменой общему user-owned профилю.
| **Выбор совместимого provider/harness** | Сильная сторона: много реальных harnesses; в Nightly можно делегировать на разные модели/providers. Прямая смена harness между turns теряет часть контекста. | Сохранить явную совместимость и предупреждать о потерях при handoff.
| **Один Secretary направляет работу в несколько Execution Nodes** | T3 управляет несколькими environments, а V2 — несколькими agent threads/providers. Документация подтверждает выбор environment для thread, но не server-owned маршрутизацию одной задачи между удалёнными nodes. | Развести выбор среды исполнения и решение Secretary о dispatch.
| **Persistent Worker, привязанный к Task** | Thread и child-thread имеют устойчивую историю и могут возобновляться; отдельная сущность Worker с долгоживущей привязкой к Task и lifecycle close не обнаружена. | Заимствовать адресуемые дочерние threads, но сохранить Worker/Task binding как самостоятельный контракт.
| **Result возвращается в Personal Conversation** | Результаты child-work видны в родительской coding thread; дифф и PR связаны с thread. Универсального Result, адресуемого обратно в межканальную Personal Conversation, нет. | Сделать именно адресованный и durable Result различием Secretary, а не просто сообщением агента.

**Вывод по совпадению:** T3 Code хорошо решает «пусть несколько coding agents работают над репозиториями, а я с телефона наблюдаю, переключаюсь, проверяю diff и PR». В Nightly V2 он уже близко подходит к мульти-harness делегированию и устойчивым дочерним thread. Он не решает пользовательский сценарий Secretary целиком: нет общего канального inbox, центрального user context, server-owned Task/Worker lifecycle и гарантированного возврата Result в одну Personal Conversation.

## 10. Что стоит взять и что выяснить дальше

**Полезные продуктовые паттерны:** изоляция каждого независимого coding task в worktree; ясная связь thread → branch → diff → PR; наблюдаемое дерево дочерних агентов; mobile как полноценная control surface для локального/удалённого host; честное отображение цены и provider usage.

**Открытые вопросы для дальнейшей проверки:** когда Orchestrator V2 станет stable и какова поддержка Nightly; какова фактическая телеметрия по умолчанию в релизных бинарниках; как удалить/export-ировать пользовательские conversation данные полностью; какие именно гарантии resume есть у каждого provider после рестарта; может ли V2 адресно размещать child-agent на другом Execution Node, а не только выбирать другой provider/model. Рекламные заявления и описания репозитория не заменяют hands-on проверку этих сценариев.
