# Персональные агенты: сравнение для Secretary

Проверено 2 октября 2026 года. Десять независимых исследовательских сессий, по одной на продукт. Исследование основано на документации, официальных страницах, GitHub и отмеченных в отчётах сторонних свидетельствах. Продукты не устанавливались и не тестировались. «Подтверждено» означает подтверждение источником, а не hands-on проверку. Недокументированная возможность не обязательно отсутствует.

Отдельное дополнение от 5 октября — [T3 Code](./t3-code.md): сверены последний Stable и Nightly, включая переход Orchestrator V2. Это дополнение не включено в исходный сводный анализ десяти продуктов.

## Что выяснилось

### Субагенты уже не отличительная возможность

У Hermes есть `delegate_task` и параллельные субагенты. У OpenClaw описаны фоновые subagents и persistent ACP sessions. У OpenHuman есть механизмы повторного использования асинхронного child context. Letta поддерживает subagents и постоянных агентов, а Grok Bot предлагает постоянных именованных Bots с взаимодействием друг с другом. Поэтому заявление «Secretary умеет делегировать, а конкуренты нет» не выдерживает проверки.

Важнее другое: может ли пользователь через обычный разговор продолжить конкретную работу у того же исполнителя, увидеть его состояние и получить результат без ручного переключения сессий? Доказательств полного одинакового контракта во всех каналах в исследованных документах недостаточно.

### Общая память не равна общей переписке

Hermes может сохранять память и историю в одном профиле, но это не подтверждает автоматическую общую conversation между CLI и Telegram. OpenHuman документирует каналы и sender sessions, но непрерывная история между поверхностями не доказана.

При этом нельзя считать идею общей переписки уникальной. OpenClaw документирует объединение direct messages при соответствующей конфигурации. Letta связывает Telegram с agent и conversation, которые можно выбрать в CLI. Эти продукты нужно проверить руками раньше, чем заявлять, что они требуют постоянного переключения контекста.

### Продолжение разговора не равно переносу рабочей среды

Delta от команды Zed добавлена десятым продуктом. Это соседняя категория: совместная coding-среда, а не универсальный персональный ассистент. Она синхронизирует thread и изменения файлов через DeltaDB, позволяя продолжить просмотр и обсуждение на вебе или телефоне без commit/push. Для Secretary это важный ориентир: одна история сообщений не переносит автоматически состояние Workspace.

Web turn в Delta не имеет локального shell и checkout; cloud runtime, CLI и ACP на проверенную дату помечены как `In Progress`. Поэтому синхронизацию данных нельзя считать гарантией продолжения исполнения при выключенном ноутбуке. У агента также не документированы permission system и sandbox. Подробности и источники в [отчёте Delta](./zed-delta.md).

### Постоянный агент не равен закреплённому за Task Worker

Именованный Grok Bot может выполнять несколько поручений. Primary dot представляет персонального помощника. Субагент может существовать только до завершения подзапроса. Conversation может сохраняться, даже когда её execution process уже остановлен.

Модель из `GLOSSARY.md` Secretary конкретнее: один Worker закреплён за Task до явного закрытия; Follow-up создаёт новую Attempt у того же Worker; результат возвращается в Personal Conversation. Это перспективная продуктовая гипотеза, но пока не доказанное преимущество работающего Secretary.

### Постоянная доступность зависит от исполнения

Для self-hosted продукта выключенный ноутбук может означать остановку Gateway или tools. Наличие сохранённой истории не означает продолжение активной работы после перезапуска. Cloud-agent может работать без ноутбука, но перестать иметь доступ к локальным приложениям или файлам.

Secretary должен показывать пользователю различие между доступностью самого Secretary и доступностью Execution node. Нельзя обещать «работает 24/7», если нужное задаче окружение недоступно.

## Предварительная продуктовая ставка

Не «ещё один бот с памятью и субагентами», а:

> Один ассистент в разных каналах. Каждая работа сохраняет своего исполнителя. Пользователь может вернуться к ней завтра, уточнить запрос и увидеть результат в той же переписке.

Для проверки этой ставки важны пять гипотез:

1. **Не нужно управлять сессиями.** Пользователь пишет «продолжи вчерашнее исправление», Secretary находит Task и Worker binding. При неоднозначности спрашивает, а не угадывает.
2. **Переписка не блокируется исполнением.** Пока один Worker работает, пользователь может обсуждать другое с Secretary. Прогресс не засоряет Personal Conversation, но доступен по запросу и в Worker observer.
3. **Follow-up действительно продолжает работу.** Сохраняются identity, runtime context и рабочая среда. Если runtime session недоступна, пользователь видит ошибку, а не незаметно нового исполнителя.
4. **Локальные и удалённые возможности объяснимы.** Пользователь видит, какой Execution node нужен Task, почему он offline и что можно сделать без него.
5. **Действия и сбои видимы.** Понятны permissions, Cancel, interrupted Attempt и Result. Нет тихого повторного запуска внешних действий после рестарта.

Это гипотезы для дизайна и проверки, не утверждения о текущей реализации и не поручения менять архитектуру.

## Единый сценарий будущего hands-on теста

1. С телефона дать ассистенту исследовательскую задачу и попросить отдельного исполнителя.
2. Не дожидаясь её завершения, дать независимую кодовую задачу.
3. Из терминала открыть ту же Personal Conversation и уточнить кодовую задачу без копирования контекста.
4. Из телефона запросить статус обеих задач, затем обратиться к нужному исполнителю.
5. Остановить или отключить Execution node. Проверить, как показаны interrupted работа и недоступные tools.
6. Вернуться на следующий день. Продолжить существующую задачу и проверить identity исполнителя и runtime session.
7. Закрыть Task. Проверить сохранение истории, артефактов и поведения дальнейшего обращения к нему.

Для продуктов без Telegram или терминала использовать поддерживаемые поверхности и явно отмечать расхождение со сценарием пользователя. Не выдавать наличие веб-интерфейса за терминальный UX.

Первые кандидаты для такого теста: Hermes как текущая база пользователя, Letta и OpenClaw как наиболее важные проверки межканального продолжения, OpenHuman как выбранный пользователем продукт, Grok Bot как ориентир постоянных исполнителей.
