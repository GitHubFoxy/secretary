# Аудит runtime для Minimal MVP

Дата: 9 октября 2026. Область: Secretary, Workers Codex/Claude Code, local/remote Dispatch, steering, `/q`, Follow-up и resume. Основание — [Minimal MVP](../../spec/THE%20spec.md), [GLOSSARY](../../GLOSSARY.md), [runtime contracts](../architecture/runtime-contracts.md). `docs/adr/` отсутствует. Это исследование: код и конфигурация не изменены, production omarchy не затронут.

## Вывод

Ближайший путь к MVP без fx/OpenCode — Secretary на Codex через уже установленный `codex-acp`, Workers Codex через тот же ACP adapter, Claude Code через доработанный native adapter, на обеих машинах существующий Execution node transport. Новую систему Dispatch, pairing или хранения Worker identity строить не требуется. Но текущие selectable adapters не равны готовому MVP: Claude Secretary несовместим с ожидаемым постоянным runtime, Claude active steering явно отсутствует, а `/q` отсутствует в актуальном Worker-first public path.

`done` ниже означает наличие реализации в коде; не утверждает реальную приёмку с платным model turn. `partial` — реализация есть, но выявлен конкретный разрыв или отсутствует native проверка. `missing` — необходимый путь отсутствует либо явно отвергается.

## Сквозные пути

**Secretary → Worker:** `cmd/secretaryd` подключает Secretary MCP и WorkerService ([main.go:334](../../cmd/secretaryd/main.go#L334), [main.go:494](../../cmd/secretaryd/main.go#L494)); MCP `spawn_worker` приходит в private HTTP route → `WorkerService.SpawnWorker` → server-owned Dispatch envelope → `NodeRuntime.send` → direct LocalCommand либо `ServerManager.SendCommand` → `ExecutionNode.dispatch` → `RuntimeRouter.Start` → `ACPRuntime.Start` или `ClaudeCodeRuntime.Start` → CLI.

**Пользователь → Worker:** UI `workerAction('message', text)` либо Telegram topic mapping → `POST /v1/workers/{ref}/message` → `phase4WorkerRoute` → `MessageWorker`. Working = Steer, idle = новый Turn/Attempt и Dispatch с PreviousAttemptID, offline = Resume. UI Follow-up button использует тот же MessageWorker, а не очередь ([App.svelte:483](../../web/src/App.svelte#L483), [observer.go:461](../../internal/webapi/observer.go#L461), [worker_lifecycle.go:626](../../internal/ctl/worker_lifecycle.go#L626)).

**Legacy queue не закрывает gap:** в old Task-based observer есть `/queue`, `WorkerController.Queue` и `acpSession.Queue`, но актуальный Worker-first route не создаёт durable queued Turn из `/q`. Это два разных пути ([observer.go:291](../../internal/webapi/observer.go#L291), [app/worker.go:71](../../internal/app/worker.go#L71), [acp_runtime.go:1337](../../internal/node/acp_runtime.go#L1337)).

## Конкретные разрывы и минимальные исправления для реализации позже

1. **Claude adapter contract.** Сохранить native Claude Code; заменить одноразовый print-only adapter на persistent input/output transport, который поддерживает deferred Start, Prompt, steering, MCP и resume одной identity. У установленного Claude есть `--input-format stream-json`, `--mcp-config`, `--include-partial-messages`; наличие flags само по себе не доказывает active steering. Проверить native behavior отдельно, затем выбрать streaming CLI либо небольшой Agent SDK adapter. Одного добавления stdin недостаточно для заявления о steering: сообщение должно попадать в активную работу, а не ждать завершения turn.
2. **Durable `/q` в одном обработчике.** Нормализовать режим сообщения у server-owned WorkerService, сохранять queued Follow-up сразу, запускать его после terminal Attempt. Web и Telegram должны использовать одну семантику. Очередь должна переживать server/node restart; одной in-memory `acpSession.queued` недостаточно. Не требуется синхронизировать Secretary model context с прямыми Worker inputs.
3. **Codex readiness того же пути, что execution.** Inventory пробует `codex`; runtime запускает `codex-acp`. Проверять наличие/версию/initialize capabilities adapter и тот Codex executable, который реально запускает adapter. Сейчас `initialize` сохраняет только protocolVersion, не проверяет advertised steering/load capabilities ([acp_runtime.go:356](../../internal/node/acp_runtime.go#L356)).
4. **Profile delivery для обоих native harnesses.** LocalNode материализует только `AGENTS.md`; Claude не получает `--system-prompt`/`--append-system-prompt` и CLAUDE.md. Remote ExecutionNode вызывает runtime непосредственно и не выполняет `MaterializeInstructions`. Metadata ACP содержит только имя/version/hash профиля, а не содержимое. Значит принятый Worker profile ещё не доказывает, что модель получила инструкции, особенно remote Claude/Codex. Использовать явный native delivery в adapter, проверить узнаваемый marker в model response. [node.go:210](../../internal/node/node.go#L210), [profile.go:124](../../internal/node/profile.go#L124), [execution_node.go:179](../../internal/node/execution_node.go#L179), [acp_runtime.go:259](../../internal/node/acp_runtime.go#L259).
5. **Co-located Node тем же durable путём, что remote.** Для MVP достаточно запускать существующий secretary-node на той же машине. Это устраняет зависимость от in-memory checkpoint direct LocalNode, без нового транспорта или migration framework.
6. **Defaults и addressed reply.** Сейчас documented/default путь ориентирован на OpenCode. Codex ACP отклоняет opt-in addressed-reply-v1 без `TerminalMessageGrouping`; этот флаг в configured Codex runtime не включён. Для минимального Codex Secretary сначала использовать существующий legacy reply contract и проверить отсутствие duplicate replies, затем отдельно расширять addressed contract. [runtime-contracts.md](../architecture/runtime-contracts.md), [main.go:703](../../cmd/secretaryd/main.go#L703), [acp_runtime.go:44](../../internal/node/acp_runtime.go#L44). Смена defaults — отдельная последующая реализация, в аудит не входит.

## Что проверено локально

Метаданные CLI: `codex --version` = `codex-cli 0.162.0`; `claude --version` = `2.1.295`; `codex-acp --version` = `@agentclientprotocol/codex-acp 1.12.0`. `codex --help` действительно показывает `doctor`, а `codex debug --help` — `models`: считать эти probe commands отсутствующими было бы неверно для этой машины.

В установленном исходнике adapter подтверждены `_session/steering`, `loadSession: true`, MCP config и чтение `CODEX_CONFIG`: [dist/index.js:33375](/opt/homebrew/lib/node_modules/@agentclientprotocol/codex-acp/dist/index.js#L33375), [dist/index.js:32337](/opt/homebrew/lib/node_modules/@agentclientprotocol/codex-acp/dist/index.js#L32337), [dist/index.js:35151](/opt/homebrew/lib/node_modules/@agentclientprotocol/codex-acp/dist/index.js#L35151). Adapter может запускать вложенный Codex package, поэтому его версия не обязана совпадать с `codex` из PATH. `codex-acp --help` начал ожидать protocol input и был остановлен; model turns этим действием не запускались.

По read-only проверке omarchy, переданной основным агентом: Secretary и Node services сейчас inactive/dead/disabled, health на 8081 не отвечает; развёрнутый binary соответствует архиву `0d1ca27`, marker deployed-commit устарел. Конфигурация обоих runtime остаётся `opencode` / `openai/gpt-6.1-luna` / `low`. На remote host Codex login status успешен, Claude auth status без загруженного service environment сообщает `loggedIn: false`; это не исключает API credential из service environment. В стандартных проверенных каталогах remote host `codex-acp` не найден. Поэтому наличие adapter на Mac не закрывает deployment gap на второй машине: самый короткий путь — установить совместимый существующий codex-acp и проверить его вместе с фактически используемым Codex executable, без переписывания Codex runtime. Эти данные не получены дополнительным обращением этого аудита к production.

Это подтверждает текущие unit/fixture contracts, а не реальную работу модели. Claude test запускает shell wrapper на test executable ([claude_runtime_test.go:30](../../internal/node/claude_runtime_test.go#L30)); public idle acceptance использует fake ACP process ([worker_idle_followup_test.go:23](../../internal/ctl/worker_idle_followup_test.go#L23)). Two-node process test тоже кладёт fake harnesses в PATH ([process_integration_test.go:45](../../internal/node/process_integration_test.go#L45)).

Следующая минимальная native приёмка после реализации: из Secretary Codex создать по одному Codex и Claude Worker на локальном paired Node и на второй тестовой машине; во время длительного действия отправить заметное steering, отдельно `/q`; убедиться, что steering меняет текущую работу, `/q` начинает новый Turn только после Result; повторить idle Follow-up с проверкой ранее сообщённого marker; перезапустить тестовый Node и продолжить ту же native session. Только эти четыре сочетания harness × machine и наблюдаемые события смогут подтвердить MVP без fx/OpenCode.
