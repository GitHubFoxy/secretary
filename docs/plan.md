# План реализации фазы 1

Ты реализуешь первую версию Secretary: свою маленькую программу, в которой владелец разговаривает с Secretary Agent, а тот поручает задачи фоновым сессиям Claude Code и Codex.

Прочитай перед началом:

- [architecture.md](architecture.md) — источник правды: компоненты, адаптеры, MCP-инструменты, таблицы, поток `delegate`, проверенные поля протоколов. План ссылается на него и не повторяет.
- [GLOSSARY.md](../GLOSSARY.md) — термины. Называй вещи в коде так же: `Session`, `Secretary Agent`.
- `spikes/` — рабочие пробные скрипты: `mcp.ts` (MCP без SDK), `claude.ts` (stream-json, resume), `codex.ts` (app-server). Бери код оттуда.

## Правила работы

- **Минимум кода.** Тестов нет. Краевые случаи не обрабатываем: если упало — пусть падает, исправим по ходу. Зависимость добавляй, только когда без неё нужно писать заметно больше кода.
- Стек: Bun, TypeScript, `bun:sqlite`, `Bun.serve` с WebSocket. Клиент — Svelte + Vite без SvelteKit.
- Структура: `server/` и `web/` в корне репозитория. Без монорепо-инструментов.
- Протокол Codex бери из генератора: `codex app-server generate-ts --out <dir>`. Типы руками не пиши.
- `ToolSearch` у Claude не отключай: решено оставить поведение по умолчанию.
- Каждый шаг заканчивается проверкой запуском. Закоммить шаг, когда проверка прошла.

## Шаги

### 1. Каркас

`server/` и `web/` с `package.json`. Bun раздаёт собранный `web/dist` и открывает WebSocket. Одна команда собирает клиент и запускает сервер.

**Готово, когда:** страница открывается в браузере, и сообщение по WebSocket доходит до сервера и обратно.

### 2. Session и адаптер Claude

Модуль `Session` с `send(text)` и `onEvent(cb)`, адаптер Claude по таблице из architecture.md. Таблицы `sessions` и `events` в SQLite. Каждое событие пишется в `events` и рассылается в WebSocket. Очередь сообщений, пока сессия занята. После `idle` процесс закрывается, следующее сообщение поднимает его через `--resume`.

**Готово, когда:** через временную кнопку или скрипт сессия Claude отвечает на два сообщения подряд, между ними процесс закрывается, и второй ответ помнит первый.

### 3. Адаптер Codex

Тот же интерфейс `Session` поверх `codex app-server`: `initialize` → `initialized` → `thread/start` / `thread/resume` → `turn/start`. Модель передаётся на каждый ход.

**Готово, когда:** сценарий шага 2 проходит на Codex, и смена модели между ходами сохраняет контекст.

### 4. MCP и delegate

Встроенный MCP-сервер на `localhost` с пятью инструментами из architecture.md. Подключается только к сессии Secretary Agent. `delegate` создаёт дочернюю сессию с `parent_id` и сразу возвращает `{id, status}`. После каждого завершённого хода дочерней сессии программа дописывает в сессию секретаря `[report #<id> <harness> <folder>] <последний ответ>`, через очередь.

**Готово, когда:** секретарь на Claude поручает задачу Codex и наоборот; отчёт приходит секретарю после хода дочерней сессии; `send`, `list`, `read`, `stop` работают.

### 5. Secretary Agent Folder

`~/.secretary/AGENTS.md` (и `CLAUDE.md`, ссылающийся на него): секретарь — правая рука владельца, отвечает сам на быстрое, поручает долгое через `delegate`, на сообщения `[report …]` молчит и пишет владельцу, только если это важно. При старте программы сессия секретаря (#1) создаётся, если её нет. По умолчанию Claude Opus.

**Готово, когда:** на просьбу «почини X в проекте Y» секретарь делегирует, а на неважный отчёт отвечает пустым текстом.

### 6. Клиент

- **Дашборд:** все сессии — статус, harness, модель, папка, последнее событие; дочерние под родителем.
- **Чат** одной сессии, одинаковый для секретаря и дочерних: поток событий вживую, поле ввода. Пустые ответы секретаря на `[report …]` скрыты.
- Выбор harness и модели для сессии. Модели Codex берутся из `model/list`. При смене harness — окно «Текущий контекст будет потерян. Продолжить / Отмена»; при «Продолжить» начинается новая сессия harness.
- `stop` кнопкой.
- PWA: manifest и иконка из `assets/icon.svg`, чтобы установить на телефон.

**Готово, когда:** весь поток из раздела «Как работает delegate» в architecture.md проходит через интерфейс, включая сообщение дочерней сессии напрямую.

### 7. Восстановление после перезапуска

При старте сессии в `running` получают `interrupted` и продолжаются через resume сообщением «продолжай».

**Готово, когда:** убийство программы посреди хода дочерней сессии и повторный запуск приводят к продолжению этой сессии.

### 8. Запуск на omarchy

Программа как сервис (systemd user unit) на omarchy, доступ через `tailscale serve` по HTTPS. Доступ к omarchy — скилл `omarchy`.

**Готово, когда:** с телефона через Tailscale открывается установленная PWA, секретарь делегирует задачу, и отчёт виден в интерфейсе.

## Вне фазы 1

Память, голос, несколько машин, облако, песочницы, Pi, перенос контекста между harness — см. «На будущее» в architecture.md. Не реализуй их.
