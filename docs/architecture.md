# Secretary v2: архитектура фазы 1

Решено 15 ноября 2026 года. Предыстория и отвергнутые варианты описаны в [discovery.md](discovery.md).

## Цель фазы 1

Владелец разговаривает с Secretary Agent в веб-чате с компьютера и с телефона. Secretary Agent поручает задачи фоновым сессиям Claude Code и Codex и сообщает результат. Всё работает на omarchy.

Принципы:

- Минимальный код. Без тестов и без обработки краевых случаев: пусть падает, исправим по ходу.
- Full access для всех агентов, без подтверждений.
- Своя программа, а не надстройка над T3 Code: голосу и телефону всё равно нужен свой клиент.

## Общая схема

```
Телефон / MacBook (PWA)
        │ HTTPS + WebSocket, через Tailscale (`tailscale serve`)
        ▼
┌──────────────── программа secretary (Bun/TS, omarchy) ────────────────┐
│ Веб-сервер: статика Svelte + WebSocket                                 │
│ Sessions: адаптеры claude / codex                                      │
│ MCP-сервер (localhost): delegate, send, list, read, stop               │
│ SQLite: sessions, events                                               │
└────────────────────────────────────────────────────────────────────────┘
        │ stdin/stdout                         ▲ MCP-вызовы
        ▼                                      │
  #1 Secretary Agent (~/.secretary) ───────────┘
        │ delegate
        ▼
  #7, #8 … дочерние сессии в папках проектов
```

## Компоненты

### Программа `secretary`

Один процесс на Bun. Код лежит в репозитории `secretary` в двух папках: `server/` и `web/`.

- **Веб-сервер.** `Bun.serve` раздаёт собранный Svelte и держит WebSocket. События всех сессий рассылаются клиенту, клиент сам показывает нужные.
- **Доступ.** Через Tailscale и `tailscale serve`: HTTPS (нужен для PWA и, позже, микрофона), сеть видна только владельцу, своей авторизации нет.

### Клиент

- Svelte + Vite, без SvelteKit. PWA, чтобы установить на телефон и на компьютер.
- **Дашборд (agent fleet):** список всех сессий со статусом, harness, моделью, папкой и последними событиями.
- **Чат:** один и тот же для Secretary Agent и любой дочерней сессии. Можно смотреть поток событий и писать.
- Пустые ответы Secretary Agent на `[report …]` не показываются.
- При смене harness (Claude ↔ Codex) появляется окно: «Текущий контекст будет потерян. Продолжить / Отмена». Модель внутри одного harness меняется без потери контекста.

### Session

Любой агент, включая Secretary Agent, — это сессия: процесс harness плюс история в SQLite. Дочерняя сессия отличается только тем, что у неё есть `parent_id`.

Интерфейс модуля: `send(text)` и `onEvent(cb)`. Внутри два адаптера:

| | Claude Code | Codex |
|---|---|---|
| Запуск | `claude --input-format stream-json --output-format stream-json --dangerously-skip-permissions` | `codex app-server` (JSON-RPC по stdio), `approval_policy=never`, `sandbox=danger-full-access` |
| Продолжение | `--resume <id>` | `thread/resume` |
| Конец хода | событие `result` | `turn/completed` |
| Смена модели | перезапуск с `--resume` и новой `--model` | модель на каждый ход |
| MCP | `--mcp-config` | `mcp_servers` в конфиге |

Жизненный цикл:

- Статусы: `running` → `idle` → `stopped`; `interrupted` после падения программы.
- После `idle` процесс закрывается. Следующее сообщение поднимает его через resume.
- Если сессия занята, обычные сообщения ждут в очереди до конца хода. Немедленная отправка (immediate) прерывает ход и запускает сообщение сразу, см. ниже.
- При старте программы сессии в `running` помечаются `interrupted` и продолжаются через resume сообщением «продолжай». Часть хода может потеряться — для фазы 1 это допустимо.
- tmux не используется: программа сама держит процессы и читает их stdout.

### MCP-сервер

Встроен в программу и слушает `http://localhost:PORT/mcp`. Подключается **только к Secretary Agent**, поэтому дочерние сессии не могут делегировать дальше и дерево остаётся одноуровневым.

| Инструмент | Что делает |
|---|---|
| `delegate(harness, model, folder, task)` | Создаёт дочернюю сессию и сразу возвращает `{id, status: "running"}`, не дожидаясь результата |
| `send(id, message)` | Дописывает сообщение в существующую сессию |
| `list()` | Сессии и их статусы |
| `read(id)` | Последние сообщения сессии |
| `stop(id)` | Останавливает процесс, статус `stopped`, история остаётся |

### SQLite

- `sessions`: `id`, `parent_id`, `harness`, `model`, `folder`, `harness_session_id`, `status`.
- `events`: `session_id`, `json`, `time`. Сырые события harness хранятся как есть, клиент рисует их сам.

### Secretary Agent Folder

`~/.secretary`: здесь работает сессия Secretary Agent. `AGENTS.md` описывает, кто он, когда поручает задачи и как реагирует на отчёты. По умолчанию Secretary Agent запускается на Claude Opus.

## Немедленная отправка (immediate)

Владелец может отправить сообщение в работающую сессию сразу. Правая кнопка «Отправить» и Enter во время хода прерывают ход и отправляют сообщение сразу. Левая кнопка «Добавить в очередь» (видна, когда сессия `running`) ставит сообщение в обычную очередь: оно уходит после конца хода, как и раньше.

Что умеют протоколы (проверено пробами `spikes/steer-claude.ts` и `spikes/steer-codex.ts`, Claude Code 2.1.325, codex-cli 0.169.0):

| | Claude Code | Codex |
|---|---|---|
| Сообщение во время хода | в stdin принимается, но учитывается на ближайшей границе вызова модели, то есть после окончания текущего инструмента | `turn/steer` дописывает ввод в тот же ход, требует `expectedTurnId`; тоже после текущего шага модели |
| Прервать ход | control-запрос `{type:"control_request", request:{subtype:"interrupt"}}`: ход заканчивается `result` с `error_during_execution`, процесс жив | `turn/interrupt {threadId, turnId}`: `turn/completed` со статусом `interrupted`, тред жив |
| Продолжение после прерывания | новый ход в том же процессе или через `--resume` (процесс у нас на каждый ход новый) | `turn/start` в том же треде |

Поэтому немедленная отправка реализована через прерывание, а не через `turn/steer`: «steer» Codex и stdin-сообщение Claude не дают мгновенного эффекта, пока инструмент не закончил работу. Сообщение, отправленное через immediate, учитывается сразу после прерывания.

Как работает в `server/session.ts`:

1. Сообщение сначала записывается в таблицу `pending_messages`, и только потом клиенту уходит подтверждение «отправлено». Поэтому подтверждённое сообщение переживает сбой и перезапуск.
2. Срочное сообщение встаёт в очередь перед обычными сообщениями и отчётами родителю, но после других срочных, которые уже ждут.
3. Если ход идёт, сессия шлёт прерывание: Claude — control-запрос в stdin, Codex — `turn/interrupt`. Если Codex ещё не начал ход (ответа на `turn/start` нет), прерывание уходит, как только адаптер его примет.
4. Прерванный ход не считается завершённым: статус не становится `idle`, отчёт родителю не уходит, очередь запускается сразу.
5. Второе срочное сообщение во время прерывания не посылает новое прерывание, а ждёт в очереди. Срочные сообщения, которые стоят в очереди к началу хода, уходят одним ходом: их тексты склеиваются через пустую строку, а в истории остаются отдельными сообщениями.
6. Если адаптер не ответил на прерывание за `Session.interruptDeadlineMs` (10 секунд), процесс убивается. Очередь запускается сама, поэтому срочное сообщение не ждёт зависшего хода бесконечно.
7. Если ход успел завершиться сам, прерывание не нужно: срочное сообщение уходит обычным путём из очереди.
8. Сообщение удаляется из `pending_messages`, когда его ход начат и сообщение записано в `events`. Если программа упала во время хода, сообщение остаётся в истории без ответа, и его не отправляют повторно.
9. После перезапуска программы сообщения из `pending_messages`, которые не успели начать ход, запускаются сами. Остановка сессии (`stop`) очищает очередь и в базе.

Проверено тестами `server/pending.test.ts` на фейковых `claude` и `codex` (`server/test-fixtures/`): срочное сообщение прерывает долгий ход и сохраняет контекст (`--resume`, тот же тред Codex), два срочных сообщения не ждут упрямый ход дольше дедлайна, зависание Codex до `turn/start` не блокирует отправку, очередь переживает перезапуск, `stop` очищает очередь.

Ограничения:

- Срочное сообщение, пришедшее во время уже идущего хода (не во время прерывания), прерывает этот ход. Предыдущее срочное сообщение остаётся в истории, но модель на него не отвечает.
- Перезапуск процесса (Claude на каждый ход, Codex — `thread/resume`) занимает несколько секунд. Это время до первого токена нового хода, не время прерывания.
- Immediate доступен только владельцу через клиент. Инструмент `send` у Secretary Agent работает как раньше.

## Как работает delegate

1. Владелец пишет секретарю: «Почини тесты в проекте X». Программа записывает событие, отправляет его в клиент и передаёт сообщение в stdin секретаря.
2. Секретарь вызывает `delegate(harness="codex", model=…, folder="~/projects/x", task=…)`.
3. Программа добавляет `#7` в `sessions` (`parent=#1`, `running`), запускает процесс в папке проекта с задачей и сразу отвечает через MCP `{id: 7, status: "running"}`.
4. Секретарь сообщает владельцу: «Поручил Codex (#7)». Разговор свободен.
5. События `#7` пишутся в `events` и рассылаются в клиент. В дашборде за ними можно следить вживую.
6. Ход `#7` заканчивается. Программа ставит `idle`, берёт последний ответ и дописывает в сессию секретаря:
   ```
   [report #7 codex ~/projects/x] <последний ответ агента>
   ```
   Если секретарь занят, сообщение ждёт в очереди.
7. По инструкции секретарь на отчёт **молчит**, и клиент пустой ответ не показывает. Если новость важная, секретарь пишет владельцу.
8. Писать в `#7` может и секретарь (`send`), и владелец прямо из клиента. После каждого хода снова выполняется шаг 6: каждый завершённый ход дочерней сессии отправляется секретарю.
9. `stop(7)` или кнопка в клиенте завершает сессию.

Если модель не будет молчать на отчёты, позже добавим маркер `NO_REPLY`, как в OpenClaw. Каждый отчёт будит секретаря и стоит токенов. Если станет дорого, начнём склеивать отчёты.

## Проверка 15 ноября: всё работает

Скрипты лежат в `spikes/` (Bun 1.4, Claude Code 2.1.318, codex-cli 0.166.0). Наш MCP — около 25 строк без SDK: stateless HTTP, JSON-ответы на `initialize`, `tools/list`, `tools/call`.

| Проверка | Claude Code | Codex `app-server` |
|---|---|---|
| Наш MCP подключается | `--mcp-config '{"mcpServers":{"secretary":{"type":"http","url":…}}}'` | `-c 'mcp_servers.secretary.url="…"'` |
| Агент вызывает `delegate` | да; перед вызовом шаг `ToolSearch` (отключается `ENABLE_TOOL_SEARCH=false`) | да |
| Сообщение в живую сессию после паузы | да, тот же процесс | да, новый `turn/start` в том же треде |
| Молчит на `[report …]` по инструкции | да, текста нет | да, `agentMessage` с пустым текстом |
| Смена модели | перезапуск с `--resume` и `--model` | `model` в `turn/start`, контекст сохраняется |
| Resume после убийства процесса + ход | 5,2 с | 4,7 с |

Уточнения по Codex:

- `thread/start`: `cwd`, `approvalPolicy: "never"`, `sandbox: "danger-full-access"`, `developerInstructions` (сюда инструкции секретаря).
- `turn/start`: `threadId`, `input: [{type: "text", text, text_elements: []}]`, `model`.
- Конец хода — уведомление `turn/completed` с `turn.status`. Текст агента — `item/completed` с `item.type === "agentMessage"`.
- Перед первым запросом: `initialize`, затем уведомление `initialized`.
- `thread/resume` с `threadId` работает, но предупреждает: полная загрузка истории устарела, лучше `excludeTurns: true`.
- Неверное имя модели не даёт ошибку на `turn/start`: ход завершается со `status: "failed"`. Список моделей — `model/list`.
- Протокол целиком генерируется: `codex app-server generate-ts --out <dir>`.

Claude Code по умолчанию откладывает схемы MCP-инструментов: модель видит только имена и сначала загружает схему через `ToolSearch`, даже если инструмент один. С `ENABLE_TOOL_SEARCH=false` шага нет, и в одном запуске `delegate` был вызван через 3,7 с вместо 7,3 с. **Пока оставляем поведение по умолчанию**; переменная — готовая оптимизация на потом. Встроенные инструменты можно сузить флагом `--tools`.

## На будущее

- **Несколько машин.** Как хост и ноды в старом Secretary. На каждой машине работает та же программа. Главная (с секретарём, клиентом и SQLite) обращается к остальным по HTTP через Tailscale, и удалённая сессия становится ещё одним адаптером. Тогда в `delegate` и `sessions` добавится поле `machine`.
- **Облако.** Тот же образ в контейнере. Cloudflare Worker будит контейнер, состояние сохраняется tar-архивом в R2. Подробности в [discovery.md](discovery.md#хостинг-локально-и-облако-решено-15-ноября).
- **Песочницы.** Для чужих серверов и VPS программа работает в Docker и видит только примонтированные папки. Позже — встроенные песочницы harness (Codex `workspace-write`, Claude Code `sandbox`). Главная угроза — prompt injection. От потери данных защищают git и бэкапы.
- **Pi** как третий адаптер через `pi --mode rpc`.
- Память, голос и кнопка Power, Specialists, перенос контекста при смене harness (хвост истории из `events`).
