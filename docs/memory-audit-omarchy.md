## 2. Разбор Secretary: что жрёт, что transient

Модель спавна (по коду `server/harness.ts`, `opencode.ts`, `codex.ts`):
каждый ход Session = `Bun.spawn` (`opencode acp`, `codex app-server`, `claude -p`),
`cwd` = папка Session, свой setsid, после хода процесс закрывается.
Изоляции нет: полный доступ, MCP-токен виден в args процесса (`architecture.md`).

Замерено на детях `bun` (PID 2801174):

| Процесс | RSS | Время жизни |
|---|---|---|
| `opencode acp` | ~90–115 МБ | на ход |
| `opencode serve` (дитя `acp`) | ~275–300 МБ | на ход |
| пара acp+serve = один активный ход (opencode) | ~400 МБ | transient |
| `codex app-server` | ~200 МБ | transient |
| `bun index.ts` (ядро) | ~50 МБ | steady |
| smart-turn + Xvfb | ~36 МБ | steady |
| helium-рендеры внутри cgroup | ~120 МБ | пока идут axi-задачи |

Cgroup целиком гуляет 1.7–2.4 ГБ вместе с нагрузкой (3 активных хода ≈ +1.2 ГБ).

## 3. Idle-футпринт одного инстанса Secretary

Чистый момент «ноль ходов» за ~10 мин наблюдений не наступил (Secretary в работе),
поэтому idle получен вычитанием transient-составляющих из `memory.current`
(проверено тремяظمة сходящимися замерами):

- Ядро idle (bun + smart-turn + Xvfb): **~90 МБ RSS**
- + тёплый браузер (axi): **~210 МБ**
- + page cache cgroup: **~0.5 ГБ** по счётчику cgroup
- Один активный ход: **+0.4 ГБ (opencode) / +0.2 ГБ (codex)**
- Типичный пик инстанса (ядро + браузер + 2 параллельных хода): **~1.3 ГБ**

## 5. Рантаймы: футпринт и изоляция под наш кейс

Кейс: Bun-процесс + периодический спавн harness (короткоживущие тяжёлые дети
по 200–400 МБ), нужен fs/net-раздел, MemoryMax на пользователя, секреты (токены)
не должны светиться соседям. Замеры оверхеда — живые (`sleep 120` под каждым):

| Рантайм | Базовый оверхед (измерено) | + на инстанс | Изоляция | Вывод |
|---|---|---|---|---|
| docker (уже стоит, rootful) | dockerd+containerd ~65–95 МБ общие | shim ~7 МБ | mnt/net/pid-NS, seccomp; но rootful = root контейнера рядом с хостом | дёшево здесь, слабее для SaaS |
| podman rootless | 0 (демона нет), conmon **2.2 МБ** | ~2 МБ | + uidmap: root в контейнере = обычный юзер снаружи | лучший баланс |
| systemd-nspawn | 0 (часть systemd) | ~0 | сильные NS, ручное управление образами/сетью | ок для dev-бокса, бедно для SaaS |
| qemu/KVM | процесс **206 МБ** idle + резерв 2 ГБ | ГБ | полная HW-изоляция | 5 инстансов = 10 ГБ резерва — не влезает |

## 6. Рекомендация

- **Рантайм: rootless Podman, по контейнеру на пользователя** (Host = контейнер,
  по GLOSSARY и ADR 0008). Причины: нулевой демон, uidmap из коробки
  (агенты работают с `--dangerously-skip-permissions`, rootful-контейнер им
  доверять нельзя), штатная интеграция с `systemd --user`, лимиты через cgroup.
  Docker оставить как есть для текущей инфры; второй стек только под Secretary.
- **Лимиты на пользователя: `MemoryMax=2G` (жёсткий), `MemoryHigh=1.2G` (мягкий).**
  Обоснование: steady ~0.5 ГБ + пик 2 ходов ~1.3 ГБ → 2 ГБ крышка с запасом,
  1.2 ГБ мягкий порог включает reclaim до OOM. Капы 5×2=10 ГБ больше RAM —
  это нормально: steady 5×0.5=2.5 ГБ + база, пики сглаживает zram.
- **Сколько влезет в 7.5 ГБ:** после освобождения ~260 МБ — **уверенно 3 инстанса**.
  Пять — только после выноса dev-нагрузки (PAG/hermes ~0.5 ГБ) с Host либо
  добавления RAM. Наращивать 3 → 5 по факту замеров steady каждого инстанса.
- Отдельно: перенести MCP-токены из args процесса (видны соседям по юзеру)
  до запуска нескольких пользователей на одном ядре — сейчас это не изоляция.
