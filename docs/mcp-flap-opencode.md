# Мигание MCP-канала secretary на OpenCode: корень и варианты чинки

Дата: 2026-11-27. Ветка: `secretary/worker-269bc17a-abf2-4280-8f2f-2e681db58391`.
Проверено кодом и живыми пробами на изолированных портах (боевые `~/.secretary`,
`secretary.service`, деплой не тронуты).

## Что наблюдается

Инструменты `send`/`list`/`read` (MCP-сервер `secretary`) пропадают у агента на
OpenCode и возвращаются. На Codex/Claude такого нет. Триггер — рестарт
`secretary.service` (обновление, падение, деплой).

## Корень (доказано)

1. **Токены MCP сгорают при каждом рестарте.** `server/sessions.ts:118-124`:
   токен генерируется `crypto.getRandomValues` в `attach()` и живёт только в
   памяти (`tokens: Map`). После рестарта все старые Bearer-токены дают `401`
   (`server/mcp.ts:281`). Проверено вживую: два подъёма `serveMcp` на одном
   порту — старый токен после рестарта отвечает `401`, новый `200` с 16
   инструментами.
2. **Окно недоступности.** `serveMcp` — `Bun.serve` на `127.0.0.1:3001` внутри
   того же процесса (`server/index.ts:154`). На время рестарта порт мёртв
   (`ECONNREFUSED`), плюс уцелевшие токены протухают (п. 1).
3. **OpenCode травит свою сессию навсегда.** Проверено вживую на
   `opencode v2.1.2` (та же версия, что на Host) против тестового MCP-сервера:
   - `session/new` с недоступным сервером → агент работает без тулов
     (`NO-PING-TOOLS`), сессия рождается отравленной;
   - `session/resume` с протухшим токеном → `initialize` даёт `401`, сервер
     выкидывается из каталога;
   - повторные `session/resume` **с правильным токеном** выполняют полное
     рукопожатие (`initialize`/`notifications/initialized`/`tools/list` — всё
     `200`), но агент всё равно отвечает `NO-PING-TOOLS`. Агент дословно
     подтверждает: *«`secretary.ping` ранее появлялся, но был удалён из
     каталога»*, `list_mcp_resources` пуст;
   - лечит только `session/new` (проверено, в том числе в той же папке).
   
   В бинарнике есть строки, подтверждающие дизайн: `mcp session expired,
   reconnecting`, `MCP server "…" is not connected … Reconnect it from /mcps`,
   `removing its tools until reconnected` — переподключение ручное
   (TUI-команда `/mcps`), автоматического восстановления каталога при
   `resume` нет.
4. **Secretary переиспользует отравленную сессию.** `server/session.ts:193`:
   каждый ход передаёт `resumeId = harness_session_id`; сбрасывается он только
   при смене harness (`configure()`, `server/session.ts:80`). Значит, один ход,
   попавший `session/resume` в окно рестарта, лишает тулов **все последующие
   ходы** этой Session. Возвращаются они только через `session/new`: новая
   Session или смена harness.
5. **Почему Codex/Claude не мигают.** У обоих MCP-конфиг живёт в процессе
   harness, который Secretary поднимает заново на каждый ход:
   - Claude: `claude --mcp-config …` + `--resume` (`server/claude.ts:4-17`).
     Резюмится только диалог, MCP переподключается свежим токеном. В `init`
     виден пер-проессный статус (`mcp_servers:[{status:failed}]`), дальше
     процесса он не живёт. Проверено: с мёртвым MCP `init` приходит, тулов
     `mcp__secretary*` нет, следующий ход с живым сервером здоров.
   - Codex: `codex app-server -c mcp_servers.secretary…` + `thread/resume`
     (`server/codex.ts:15-17,66-68`). Проверено: с мёртвым MCP `thread/start`
     успешен (`THREAD OK`), сервер уходит в `starting` → transport fatal,
     тред продолжается; следующий процесс всё перечитывает заново.
   
   То есть у них битый ход изолирован одним ходом, у OpenCode — poisoning
   персистентен в `~/.local/share/opencode/opencode.db` и переживает процессы.

Попутное наблюдение (не корень, но отличие): только OpenCode ходит по
Streamable HTTP — после `initialize` открывает GET SSE-поток
(`Accept: text/event-stream`). Наш сервер отвечает `405` на любой не-POST
(`server/mcp.ts:279`). На практике безвредно: рукопожатие идёт дальше,
ретраев в простое нет (проверено 30+ с тишины, ретраев при лежащем сервере
тоже нет — клиент пассивен до следующего `resume`/`prompt`).

## Почему «пропадают и возвращаются»

- Ход, чей `session/resume` попал в окно рестарта (сервер down и/или токен
  уже/сразу протух), травит opencode-сессию → тулов нет во всех следующих
  ходах.
- Сессии, простаивавшие во время рестарта, следующим ходом делают `resume`
  уже с новым токеном на поднявшийся сервер → здоровы. Отсюда прерывистость.
- Возврат — через `session/new`: новая Session, смена harness в настройках
  (сбрасывает `harness_session_id`), удаление/создание заново.

## Варианты чинки (без изменения кода в этой ветке — только оценка)

1. **Сбрасывать `harness_session_id` opencode-сессий при загрузке после
   рестарта** (`Sessions.load`, `server/sessions.ts:43-56`: для строк с
   `harness='opencode'` обнулить `harness_session_id` в БД). Следующий ход
   пойдёт через `session/new` + уже существующий механизм догрузки истории
   (`chatTranscript`, `server/session.ts:193`) — тот же путь, что сегодня при
   смене harness. Закрывает именно заявленный сценарий (яд после рестарта).
   Цена: теряется нативный контекст opencode-сессии (его саммари/снапшоты),
   первый ход после рестарта длиннее на историю. Отравление без рестарта
   (редкие подвисания `:3001`) не закрывает. Оценка: ~0.5 дня + тесты.
2. **Стабильные токены между рестартами** (хранить в БД/файле, ротировать
   явно). Убирает класс отравлений через `401`, но не чинит окно
   недоступности (`ECONNREFUSED` в момент `resume` травит так же). Само по
   себе недостаточно; имеет смысл только в паре с п. 1 или 3. Оценка:
   ~0.5–1 день (миграция, права на файл, ревью безопасности — токен сегодня
   специально эфемерный, см. `architecture.md:43`).
3. **Детект слепоты и принудительный `session/new`.** После `resume` адаптер
   не видит каталог тулов агента (в ACP v1 нет API статуса MCP), поэтому
   детект только косвенный (эвристики по событиям/ошибкам хода) — хрупко.
   Оценка: 2–3 дня, риск ложных пересозданий сессий.
4. **Апстрим в OpenCode** (восстанавливать сервер в каталоге при успешном
   `tools/list` на `resume`, авто-reconnect вместо ручного `/mcps`).
   Правильное место, но вне нашего контроля по срокам; issue + тест сверху.

Рекомендация: п. 1 (дешево, бьёт в заявленный сценарий) + issue апстриму
(п. 4). П. 2 — только если захотим пережить рестарт без потери контекста,
но это уже оптимизация, а не чинка.
