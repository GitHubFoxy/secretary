# Secretary

Secretary App — приложение для всех, кто хочет поручать работу ИИ-агентам. Пользователь разговаривает с одним Secretary Agent с телефона (Capacitor) или в браузере. Secretary Agent отвечает сам или поручает работу Specialists — сессиям Claude Code и Codex на Host. Пока единственный пользователь — разработчик.

Цель — массовая параллельная работа. Пользователь отдаёт Secretary Agent любые задачи и всегда может с ним говорить. Secretary Agent раскладывает задачи по Specialists в папках проектов. Specialist сам распараллеливает работу: каждую фичу реализуют и проверяют в отдельном git worktree, затем Specialist сливает готовое. Проектирование — в issue #33.

Перед работой прочитай:
- `GLOSSARY.md` — термины. Используй их и не подменяй синонимами.
- `docs/architecture.md` — как устроена программа.
- `docs/discovery.md` — почему приняты решения и что отвергнуто.

## Устройство

- `server/` — Bun + TypeScript, без npm-зависимостей: `Bun.serve` (HTTP + WebSocket), `bun:sqlite`, адаптеры Claude Code и Codex, MCP для Secretary Agent.
- `web/` — Svelte 5 + Vite + Tailwind, без SvelteKit. Код на JavaScript.
- `web/android` — Capacitor-оболочка. Приложение загружает `https://app.scrtrbot.ru`, поэтому изменения интерфейса доходят до телефона без переустановки APK. Пересобирать APK нужно только при изменениях нативной части.
- Протокол Codex в `server/protocol/` сгенерирован: `codex app-server generate-ts --out <dir>`. Не правь его вручную.

## Разработка

- Запуск: `bun install --cwd web`, затем `bun run start`. Сервер слушает `127.0.0.1:3000`.
- На omarchy программа работает как пользовательская служба `secretary.service`. Изменения сервера вступают в силу после `systemctl --user restart secretary.service`.
- Публикация интерфейса: `bun run --cwd web build`. Открытые клиенты подхватывают новую версию сами.
- Тесты: `bun test` в `server/` и в `web/`.

## Как писать код

- Код должен читаться за один проход. Если задачу можно решить меньшим количеством кода, решай меньшим.
- Решай задачу из issue, а не соседние.
- Перед изменением спроси: должны ли эти части меняться вместе? Что меняется вместе — лежит рядом, по фиче, а не по слою. Что меняется по разным причинам — не связано.
- Не копируй логику и значения. У каждого правила одно место в коде.
- Явное лучше неявного: никаких глобальных флагов, порядка вызовов или соглашений, которые вызывающий должен «просто знать».
- Особый случай — `if` для одного значения, параметр для одного вызывающего, проглоченное исключение, retry или sleep — признак, что дизайн чего-то не учёл. Найди общее решение вместо ещё одного особого случая.
- Не пиши обёртки, которые только пересылают вызов, настройки и точки расширения «на будущее». Мёртвый код удаляй.
- Комментарий нужен, только когда код не может показать причину сам: внешнее ограничение, обход чужого бага. Не пересказывай код.
- Тест должен падать при регрессии и только тогда. Проверяй поведение, а не внутренности. Не пиши тесты, которые повторяют реализацию или не могут упасть.
- Главная проверка — запуск: открой приложение и убедись, что изменение работает.
- Новую зависимость добавляй, только когда без неё кода станет заметно больше.
