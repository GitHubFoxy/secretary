# 29 Не повторять Worker Result отдельным ответом Secretary

Type: task
Status: claimed

## Work

Инцидент 3 октября 2026 после deploy `459709c`: пользователь спросил в Telegram General о текущей погоде. Worker `wrk_153669ff80fa91c6f9b779214962a817` закончил работу, Result был доставлен в General, затем Secretary отдельным сообщением пересказал тот же результат и процесс делегирования.

Это нарушает contract прямой доставки Result без дополнительного Secretary turn. По скриншоту нельзя определить, был ли создан новый turn или продолжился первоначальный turn Secretary. Проверить оба пути, event chronology и фактически загруженный external Profile. Не объявлять automatic turn причиной без доказательств.

Default `internal/config/defaults/secretary.md` уже запрещает delegation narration и повторение автоматически доставленного Worker Result. Один дополнительный запрет в default prompt не доказывает исправление: существующие external Profiles не перезаписываются при deploy.

## Acceptance

- На одно terminal завершение Worker пользователь получает один canonical Result в General и его предусмотренную копию в Worker Topic, а не дополнительный пересказ Secretary.
- Result delivery не создаёт automatic Secretary turn.
- Если первоначальный Secretary turn ещё активен, он не повторяет уже доставленный Result и не публикует narration "Попросил Worker... дождался результата".
- Новое сообщение пользователя после Result по-прежнему запускает нормальный Secretary turn. Нельзя подавлять все ответы после dispatch.
- Durable replay/restart не создаёт дубли. Дедупликация по идентичности события/Result, не по совпадению текста.
- Проверяется реальный external Profile; пользовательские инструкции и история не перезаписываются без явного согласия.
- Tests различают повторную доставку, новый automatic turn и дублирование внутри исходного turn.

### Owner-ready proposal: versioned addressed reply v1

**Предпочтительный scope:** добавить отдельную server-owned MCP operation `reply_to_user`, не выводить назначение текста из ACP `messageId`, guessed native tool name, regex или сходства текста. Operation принимает `secretary_turn_id`, server-issued `input_id` и полный `text`; Secretary server проверяет, что оба ID принадлежат capability/Conversation и ещё активному originating turn. Для одной пары `(secretary_turn_id, input_id)` reply сохраняется idempotently один раз. Тот же `input_id` передаётся как origin metadata в принятые `spawn_worker`/`message_worker` calls; Core хранит связи origin → все принятые Worker Turns → их exact Result IDs. Это покрывает несколько задач одним originating turn.

В `addressed-reply v1`, если canonical Worker Result связан с exact originating pair до завершения turn, непомеченный terminal Summary не становится вторым user-facing reply; явный независимый ответ сохраняется через `reply_to_user`. Если связанного Result нет, legacy unaddressed terminal output сохраняется. Пока для exact originating pair нет linked canonical Worker Result или typed reply, валидные pre-Result ACP `ActivityText` продолжают stream без буферизации. После durable принятия связанного Result новые unaddressed deltas и непомеченный terminal `Result.Summary` не публикуются; уже опубликованные до Result дельты не удаляются. Без связанного Result прежний ответ сохраняется. Прямой ответ вместе с Dispatch, acknowledgement, clarification, объяснение ошибки и ответ после failed Dispatch остаются возможны через `reply_to_user`; failed Dispatch без принятого Worker не создаёт origin Result. Ошибки самого runtime остаются видимыми через существующий terminal turn status/error. Никакой automatic Secretary turn не добавляется. Worker Result identity/replay остаются ответственностью существующего Core store.

**Совместимость и цена:** это additive MCP/Core/API contract; существующие lifecycle tool schemas сохраняются, origin fields и таблицы связей добавляются без backfill старой истории. Старые ACP adapters продолжают отдавать `Result.Summary`; старые sessions/profiles остаются в явно legacy behavior и не объявляются исправленными. V1 включается только для совместимого runtime/Profile после отдельного owner-approved opt-in; внешний Profile или историю автоматически не перезаписывать, production не менять. V1 не опирается на native ACP tool names: `reply_to_user` поступает из отдельного server-owned MCP handler. Цена — отдельный вызов инструмента, IDs/context и durable origin relation в Worker actions, новая атомарная reply запись/идемпотентность. Выбранное streaming поведение сохраняет pre-Result responsiveness, но не может отозвать narration, уже показанную до Result; suppression гарантируется только для последующего unaddressed output после exact Result link. Полный typed chunk/finish протокол не входит в минимальный scope.

**Решение владельца: YES.** В batch instructions зафиксировано явное согласие на owner-ready `addressed-reply v1` для локальной реализации. Это не разрешение автоматически переписывать external Profiles/history, production state или bindings.

### Follow-up: поздний authenticated `respond_worker` outcome — локально исправлено, acceptance gates открыты

**Root cause:** `NodeRuntime.Respond` ждёт outcome через `ServerManager.SendCommandAndWait`. После успешной отправки timeout/cancellation возвращались как обычная ошибка; `WorkerService.deliverCommand` записывал `failed`, хотя это не доказывает отказ Node. `SendCommandAndWait` удалял waiter при возврате, а production assembly не подключала durable command-outcome sink. Поэтому поздний authenticated accepted receipt не обновлял Core, а Result, пришедший между timeout и receipt, мог потерять exact origin relation из-за `failed` state. Дополнительно ветка `WorkerNeedsInput` затеняла `err`: ошибка handoff терялась, а после timeout мог возвращаться лишь `context deadline exceeded` из следующего Core query.

**Изменения в approved scope:**

- `internal/node/server_manager.go`: транспортный write error, wait timeout и interrupted/unknown response outcome классифицируются как неизвестный результат, не как отказ. Authenticated outcome сначала проходит durable sink, и только после его успешной записи разблокирует waiter; поздний receipt обрабатывается и без waiter.
- `internal/node/store_command_outcome_sink.go` подключён в production assembly (`cmd/secretaryd/main.go`). Он передаёт только `respond_worker` receipts в Core. Старые `response_failed` и ошибки после вызова native responder считаются uncertain; явный отказ до попытки ответа остаётся denied.
- `internal/core/worker_command_receipt.go`, `phase4_types.go`, `phase4_store.go`: receipt хранится durable с authenticated Node, command kind и exact Attempt/Turn; mismatched Node/Turn/Attempt отклоняется. Accepted завершает exact command и идемпотентно связывает его origin; denied остаётся terminal до явного retry; accepted receipt для такого retry может supersede denial. Повторные и устаревшие receipts не понижают accepted. Late accepted response возвращает только ещё ожидающий `needs_input` Turn в active; уже terminal Turn не оживляется. Uncertain intent остаётся eligible для Result только на exact Worker Turn до прихода receipt.

### Follow-up: Approval intent и terminal Turn — local implementation, combined gate PASS; manual acceptance открыта

Полностью прочитан `/private/tmp/secretary-luna-final-review/spec.md`. Оба blocking findings воспроизведены: Node receipt с фактом `accepted` не сохранял исходный выбор Approval, а прямой `ApprovalApproved` мог вернуть terminal Turn в `active`.
