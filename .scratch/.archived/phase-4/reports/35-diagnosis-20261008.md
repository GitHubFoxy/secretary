Исследованы два сообщения со скриншота: вопрос о погоде в Барнауле и вопрос о дате выхода фильма Resident Evil. Все времена ниже — UTC+7. Работа ограничена диагностикой: рабочий код, production config, процессы, credentials, DB и bindings не менялись; сообщений боту и новых model calls не отправлялось.

## Вывод

Обнаружены два независимых сбоя:

1. **Ответы Secretary сохранены, но Telegram bridge их пропускает.** Канонический Addressed reply публикуется как `conversation.entry`, а bridge не обрабатывает этот тип события. Он продвигает durable cursor без постановки ответа в Telegram outbox. Это подтверждено production event log/state и локальным воспроизведением на настоящих функциях bridge/adapter.
2. **Оба `spawn_worker` отклонены из-за несовместимого reasoning pin.** Secretary явно выбрал FX, хотя deployment defaults — OpenCode. Для FX отсутствуют observed reasoning levels; запрос `low` отклоняется. Во втором запросе reasoning не указан, но наследуется из Worker policy. Workers не созданы, поэтому результатов по вопросам нет.

**Зависание Secretary после второго сообщения в этом эпизоде не подтверждается.** Оба turn завершились `succeeded`, каждый сохранил один Addressed reply. Второй input поступил уже после завершения первого turn. Исследованные сообщения не проверяют steering во время active turn и `/q`.

## Почему Telegram не показал сохранённые ответы

Путь записи корректен: `reply_to_user` вызывает `RecordSecretaryReply`, который сохраняет `EntrySecretary` и связь с точной парой turn/input. `appendEntryWithIdentity` публикует `conversation.entry` с текстом в поле `body`.

На production оба reply events имеют `source=server`, непустой `body` и пустой `worker_ref`. Дальше:

- `cmd/secretaryd/telegram.go:165`, функция `telegramEvent`: извлекает `text/summary/result/error/response`; `body` читает только для `message.saved`. Ветка `conversation.entry` отсутствует, поэтому default на строке 260 обнуляет `Kind`.
- `internal/telegram/adapter.go:714`, функция `handleEvent`: событие с пустым Kind и без WorkerRef ничего не отправляет и возвращает `nil`.
- `internal/telegram/adapter.go:676`, функция `HandleDurableEvent`: после этого успешного возврата сохраняет новый cursor.
- `queueSecretary` на строке 920 собирает текст из `secretary.text_delta` и `secretary.turn.finished`, но ни одного пригодного источника текста для этих turns нет.

Оба terminal events подтверждают одинаковый contract:

```text
status=succeeded
branch=addressed_reply_only
terminal_class=end_turn
assistant_chunks=0
reply_count=1
terminal_valid=true
rpc_succeeded=true
drain_completed=true
entry_present=true
response_present=false
committed=true
code=completed
```

У `secretary.turn.finished` нет top-level `text/summary/result/error/response`. Ноль assistant chunks здесь допустим: пользовательский ответ уже сохранён через MCP. Старый путь Telegram, ожидающий deltas или terminal text, не покрывает этот contract.

При инспекции `telegram/state.json`: `last_event_seq=7387`, `secretary_ready=true`, pending text/tools/event sequences отсутствуют, outbox отсутствует. Следовательно, reply events 7376 и 7385 уже пройдены, но отправка не была поставлена в очередь. Повторное обычное чтение после этого cursor не вернётся к ним.

В таблице `deliveries` обнаруженные pending записи имеют target `conversation`. Это не Telegram outbox и само по себе не доказывает отказ Bot API.

## Почему не запустились Workers

Оба `mcp.tool_result` содержат одну и ту же безопасную диагностическую ошибку:

```text
core: invalid dispatch pin: core: requested harness pin is unavailable:
reasoning "low" is not observed by omarchy/fx
```

Первый tool call явно выбирает FX, модель `gpt-6-luna` и reasoning `low`. Второй снова явно выбирает FX и ту же модель, но опускает reasoning. `effectiveDispatchPins` (`internal/core/dispatch_resolver.go:111`) подставляет `worker_policy.reasoning=low`, поэтому отказ повторяется.

Observed FX inventory: `ready`, нужная модель есть, `reasoning_levels=[]`. OpenCode inventory также ready и объявляет `low`. Config Secretary и Worker defaults: `opencode`, `openai/gpt-6-luna`, `low`; Secretary reply contract — `addressed-reply-v1`. Явный выбор FX ограничивает resolver: он не переключает такой запрос на OpenCode автоматически. За исследуемый период новых Workers создано **0**.

Почему модель предпочла FX, однозначно из доступных безопасных логов установить нельзя. В сохранённых context snapshots есть прежние FX bindings и acceptance-контекст; Secretary profile не содержит literal FX instance pin. Это возможный источник выбора старых preferences, но не доказательство внутренней причины решения модели. Подтверждённая причина отказа — сочетание explicit FX и несовместимого `low`, а не отсутствие OpenCode auth/readiness.

## Проверка альтернативных объяснений

1. **Пропуск канонического reply event — подтверждён.** Оба reply events сохранены, cursor их прошёл; локальный стенд воспроизводит отсутствие отправок.
2. **Ошибка отправки уже поставленного в Telegram outbox ответа — не подтверждена.** Для этих событий код до outbox не доходит. В journal исследуемого интервала нет ошибок `sendMessage`; отсутствие такой строки само по себе не считалось доказательством.
3. **Telegram rate limit блокировал эти replies — исключён как причина их пропуска.** В journal в 10:49:30–10:49:51 есть `createForumTopic` HTTP429 для старого event 7333/cursor 7332. К моменту сообщений cursor уже дошёл дальше; позднее он достиг 7387. Сбой выше воспроизводится без Telegram и без rate limit. Ранний 429 остаётся отдельным фактом.
4. **MCP discovery/provider/terminal stall — не подтверждён для этих turns.** Для обоих: startup/initialize/tools_list успешны, девять tools, `has_spawn_worker=true`, `has_reply_to_user=true`, `failed=false`; native ACP log фиксирует prompt и response, Core подтверждает RPC/drain/end_turn.

Реакция 👀 устанавливается после успешного принятия input сервером. Typing также отправляется при приёме сообщения и при открытом turn. Эти индикаторы не зависят от успешного Dispatch или видимого ответа. В исследованном коде реакция не является индикатором terminal completion.

## Воспроизведение без исправления

Диагностический стенд сохранён отдельно: `35-diagnostic/replay_test.go.txt`. Он использует существующие `bridgeTransport`, `bridgeServer`, настоящую функцию `telegramEvent`, настоящий `Adapter.HandleDurableEvent` и `Flush`. Go overlay подключает тест только на время запуска; production Go-файлы не меняются. Payloads синтетические, но повторяют найденную форму событий.

Из корня repository:

```sh
python3 - <<'PY'
import json, pathlib, subprocess, tempfile
root = pathlib.Path.cwd()
source = root / '.scratch/.archived/phase-4/reports/35-diagnostic/replay_test.go.txt'
with tempfile.TemporaryDirectory(prefix='p4-35-diagnostic-') as directory:
    overlay = pathlib.Path(directory) / 'overlay.json'
    overlay.write_text(json.dumps({'Replace': {
        str(root / 'cmd/secretaryd/p435_diagnostic_test.go'): str(source)
    }}))
    result = subprocess.run([
        'go', 'test', '-overlay', str(overlay), './cmd/secretaryd',
        '-run', '^TestP435Diagnostic$', '-v', '-count=1'
    ])
raise SystemExit(result.returncode)
PY
```

Выполнено первоначально один раз, затем с `-count=2` и ещё раз приведённой выше командой после сохранения стенда. Все четыре запуска дали одинаковый результат:

```text
two_inputs_typed_reply: consumed_events=6 cursor=6 sends=0 want=2 — FAIL
minimal_typed_reply:    consumed_events=2 cursor=2 sends=0 want=1 — FAIL
legacy_delta_control:  consumed_events=2 cursor=2 sends=1 want=1 — PASS
```

Минимальный вариант оставляет `conversation.entry` и `secretary.turn.finished`. Started/input events, MCP вызовы, настоящий transport, модель и второй turn для потери одного reply не нужны. Второй turn повторяет тот же дефект. Контроль меняет источник текста на прежний `secretary.text_delta` и получает отправку. Это локальный deterministic repro потери доставки, не новый live Telegram acceptance и не воспроизведение модельного выбора FX.
