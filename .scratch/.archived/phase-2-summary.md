# Phase 2: Архитектура независимого Secretary и первый Thin Vertical Slice

Дата: Сентябрь 2026.

Этот документ фиксирует архитектурные решения, спецификацию, перечень задач, результаты реализации и приёмочные доказательства Phase 2 до удаления каталога `phase-2/`.

---

## 1. Контекст и проблема

Ранние прототипы (AgentHub и Bridge) доказали жизнеспособность концепции постоянных воркеров (persistent Workers), диспетчеризации (Dispatch), получения результатов (Result) и последующих уточнений (Follow-up). Однако они представляли собой лишь демонстрационный каркас (POC) и не годились в качестве целевой продуктовой архитектуры.

Целью Phase 2 стало создание независимого персонального Secretary:
- Единый сервер на Go с постоянным хранилищем в SQLite.
- Одна непрерывная Личная беседа (`Personal Conversation`) для пользователя во всех клиентских интерфейсах.
- Четкое разделение ответственности между компонентами через подключаемые адаптеры каналов (`Channel adapters`) и узлы исполнения (`Execution nodes`).
- Первый минимальный сквозной вертикальный срез (`thin vertical slice`): Web-интерфейс → Secretary → локальный воркер на Codex → наблюдение и управление воркером (Steering / Stop) → возврат результата без зависимости от сторонних хабов.

---

## 2. Ключевые архитектурные решения

1. **Единый источник правды (Server as Source of Truth):**
   - Go-сервер владел сущностями: Пользователь (`Person`), Личная беседа (`Personal Conversation`), записи беседы (`Conversation entries`), Задача (`Task`), привязка воркера (`Worker binding`), Попытка (`Attempt`), Результат (`Result`) и жизненный цикл.
   - Идемпотентность входящих событий обеспечивалась по ключу `(adapter_id, external_message_id)`.
   - Результаты воркера принимались идемпотентно по `(worker_ref, attempt)`.

2. **Модель постоянного Secretary:**
   - Secretary являлся отдельной постоянной сессией Codex ACP на узле по умолчанию.
   - Управление жизненным циклом задач происходило исключительно через CLI-утилиту `secretaryctl` с ротируемым токеном возможностей (`capability-scoped`). Сервер хранил только хеш токена.
   - `secretaryctl` поддерживал строго типизированные команды: создание задачи, повторный диспетч, закрытие, просмотр и листинг.

3. **Конечный автомат задачи (Minimal Task State Machine):**
   - **Жизненный цикл Task:** `dispatching` → `dispatch_failed` | `open` → `closing` → `closed`.
   - **Жизненный цикл Attempt:** `starting` → `active` → `succeeded` | `failed` | `canceled` | `interrupted`.
   - При сбое диспетчеризации задача сохранялась в статусе `dispatch_failed` без создания привязки воркера и без автоматического бесконечного ретрая.
   - Завершение попытки (`succeeded` / `failed` / `canceled`) оставляло задачу в статусе `open` для возможности отправки Follow-up.
   - Закрытие задачи при активной попытке сначала инициировало `Cancel` и дожидалось терминального результата перед архивацией.
   - Перезапуск сервера или ноды переводил активные попытки в `interrupted` без автоматического повторного выполнения.

4. **Адаптер узла исполнения (Execution Node & Codex Runtime):**
   - Узел управлял средой исполнения и процессом Codex ACP (использовался pinned upstream `agentclientprotocol/codex-acp`).
   - Поддерживался стандартный ACP `Cancel` (транслировался в Codex interrupt) и согласованное расширение `_session/steering` (транслировалось в Codex `turn/steer`).
   - Если рантайм временно не поддерживал steering во время активного шага, узел сохранял ввод в состоянии ожидания до наступления `idle`.
   - Подтверждение готовности сессии требовалось до завершения принятия Dispatch.

5. **Канальный адаптер и наблюдение за воркером (Channel Adapter & Worker Observer):**
   - Первый клиент: Web с обменом одноразового bootstrap-токена на безопасную сессионную cookie (`HttpOnly`).
   - Синхронизация беседы по WebSocket с гарантированным порядком: клиент передавал последний полученный `entry_seq`, сервер атомарно воспроизводил пропущенные записи и затем переходил на live-доставку.
   - Наблюдатель за воркером (`Worker observer`) получал текущий статус воркера и подписывался исключительно на прямой поток активности (`live-only activity`). Сырой вывод инструментов не засорял общую беседу и не транслировался другим клиентам.
   - Через observer пользователь мог передать Steering, поставить сообщение в очередь (`/q`) или нажать Stop (переводящий статус в `stopping` до подтверждения отмены).
   - Терминальный Result возвращался в Личную беседу в исходном виде (`verbatim`) и не порождал новый виток рассуждений Secretary.

6. **Осознанно отложенные функции (Out of Scope):**
   - Встроенное управление репозиториями (`Project management`, `create_project`, аренда чекаутов): воркер выполнял git clone и git worktree напрямую через shell.
   - Многопользовательский режим, связывание аккаунтов (account linking), ACL.
   - Удаленные ноды, TLS, песочницы (sandbox) и проверки прав доступа (все выполнялось с полным доступом пользователя ОС).
   - Поддержка Telegram / Slack (только Web в первом срезе).

## 4. Приёмочные доказательства (Acceptance Evidence)

1. **Автоматизированное детерминированное тестирование:**
   - Настоящий Go-сервер, временная база данных SQLite, встроенная локальная нода и процесс-заглушка Fake ACP (`internal/node/fake_test.go`).
   - Сквозные тесты покрыли: логин владельца, упорядоченную синхронизацию беседы, подтверждение Dispatch со ссылкой на воркера, передачу активности в observer, Steering, Cancel и возврат Result.
   - Отдельные тесты подтвердили дедупликацию входящих адаптеров, идемпотентность результатов, статус `dispatch_failed`, корректный перевод в `interrupted` при рестарте и безопасное закрытие задачи.

2. **Ручная валидация на реальных компонентах:**
   - Запуск с закрепленной версией `agentclientprotocol/codex-acp` v1.10.0, локальной авторизацией Codex и моделью `gpt-5.6-luna`.
   - Подтверждена работоспособность полного цикла: вход через браузер → поручение задачи Secretary → запуск локального воркера → управление через Steering/Stop → появление финального результата в общей беседе.

---

## 5. Итоги и переход к следующим фазам

Phase 2 успешно сформировала стабильное ядро системы на Go и SQLite, доказав независимость Secretary от legacy-компонентов. Полученный опыт и архитектурные ограничения легли в основу Phase 3 (добавление CLI, launchd, внешних профилей, нескольких харнессов и интерфейса на Svelte) и Phase 4 (распределение на несколько машин и переход к модели Worker-first).
