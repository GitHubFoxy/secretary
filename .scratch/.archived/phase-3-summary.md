# Phase 3: Полировка Local-First Secretary, профили и multi-harness поддержка

Дата: Сентябрь – Октябрь 2026.

Этот документ фиксирует цели, архитектурные решения, реализацию компонентов, перечень тикетов и приёмочные доказательства Phase 3 («polishing») до удаления каталога `phase-3-polishing/`.

---

## 1. Цели фазы

Превратить локальный прототип Secretary в законченный продукт для ежедневного использования:
- Запуск и управление одной командой через CLI `secretary` с поддержкой `launchd` демонизации в macOS.
- Полноценный мобильный интерфейс пользователя на Svelte и Tailwind CSS, встраиваемый непосредственно в Go-бинарник.
- Отдельная панель управления (`Control Room`) для отладки, инспекции деревьев воркеров, логов и конфигурации.
- Внешние текстовые конфигурации (TOML) и профили агентов (Markdown) с атомарной перезагрузкой на лету.
- Протокол жизненного цикла инструментов через серверные MCP-серверы (`server-owned MCP tools`).
- Дерево дочерних воркеров (`Child Worker Tree`) с ограничением глубины и параллелизма.
- Поддержка трех агентских сред (harnesses): OpenCode (основной профиль-ориентированный), Codex и `fx` (адаптеры совместимости).

---

## 2. Ключевые архитектурные решения и компоненты

### 2.1. CLI и инфраструктура жизненного цикла (`secretary`)
- Бинарные файлы устанавливаются в `~/.local/bin`, рабочее состояние — в `~/.local/share/secretary`.
- Единый CLI `secretary` реализует команды: `setup`, `preflight`, `start`, `stop`, `restart`, `status`, `logs`, `doctor`, а также установку/удаление службы `launchd` (`launchd install/uninstall`).
- Флаг `--debug` активирует режим отладки и открывает доступ к Control Room по адресу `/control-room`.
- Передача учётных данных первоначального сопряжения (pairing) выполняется безопасно через URL fragment (хэш в адресной строке), не попадая в серверные логи.

### 2.2. Внешняя конфигурация и компилируемые профили
- Конфигурация хранится в TOML, а профили — в виде внешних Markdown-файлов:
  - `secretary` (профиль секретаря),
  - `worker` (профиль основного исполнителя),
  - `child_worker` (профиль дочернего воркера).
- При старте и по сигналу `SIGHUP` конфигурация и профили компилируются в неизменяемые снимки (`immutable snapshots`).
- Перезагрузка атомарна: синтаксическая ошибка или сбой записи события оставляет текущую активную конфигурацию неизменной.
- Каталог моделей доступен только секретарю через инструмент `available_models_for_worker` и только по прямому запросу пользователя. Воркеры используют абстрактные алиасы: `fast`, `smart`, `cheap`.

### 2.3. Журнал событий и политика хранения (Retention)
- Нормализованные события жизненного цикла сохраняются в SQLite.
- Сырые потоки протокола ACP логируются в формате JSONL с покадровой ротацией.
- Политика очистки по умолчанию: хранение логов до 30 дней и не более 1 GiB общего объема. Рабочие директории закрытых задач архивируются и удаляются через 30 дней.

### 2.4. Серверные инструменты MCP (Server-Owned MCP Tools)
- Инструменты MCP предоставляются агентам через изолированный stdio-хелпер, создаваемый на каждую сессию.
- Secretary получает инструменты управления жизненным циклом задач, авторизуемые через capabilities.
- Основной Worker получает только инструмент `spawn_subagent`.
- Child Worker не получает никаких инструментов управления и не может бесконечно ветвить подзадачи.
- Все вызовы инструментов строго аудируются в общем журнале событий.

### 2.5. Дерево дочерних воркеров (Child Worker Tree)
- Дочерние задачи персистентны, привязаны к конкретной попытке родительского воркера (`parent Attempt`).
- Лимиты: глобально не более 4 активных воркеров одновременно; родитель может породить не более 4 дочерних воркеров за одну попытку.
- `spawn_subagent` является блокирующим вызовом для родителя: после генерации результата дочерний воркер автоматически закрывается, а его результат возвращается родителю в ответ на вызов инструмента.
- Результаты дочерних воркеров никогда не попадают напрямую в Личную беседу пользователя, предотвращая информационный шум.

### 2.6. Поддержка множества харнессов (OpenCode, Codex, fx)
- **OpenCode (целевой harness):** запускается с нативным конфигурационным файлом агента на сессию, передает метаданные профиля через ACP `_meta`, автоматически подтверждает запросы прав доступа (full-access policy), поддерживает неизменяемые снимки возобновления (`resume snapshots`).
- **Codex и fx (адаптеры совместимости):**
  - Работают через общий ACP compatibility adapter.
  - Codex использует скомпилированный `AGENTS.md` и бутстрап-промпт.
  - `fx` реализует steering через перехват (`interrupt`), ожидание состояния `idle`, создание сохраняемой попытки Follow-up и продолжение работы с новым промптом.
  - Отсутствующие или неподдерживаемые в системе харнессы приводят к явной диагностической ошибке без скрытого отката.

### 2.7. Пользовательский интерфейс (User UI) и Control Room
- Созданы на базе Svelte и Tailwind CSS, скомпилированы в статичные production-бандлы и встроены в бинарник через `go:embed`.
- **User UI:** тёмная тема, mobile-first верстка, вход по сессионной cookie, мастер онбординга из 4 шагов, выбор модели, лента беседы, карточки воркеров и адаптивная панель наблюдения (боковая шторка на десктопе или полноэкранный режим на мобильных).
- **Control Room:** доступен только в режиме `--debug` по пути `/control-room`. Отображает общее состояние системы, интерактивное дерево воркеров, ленту нормализованных событий, сырые ACP-логи, экспорт данных и интерфейс редактирования конфигурации с валидацией.

## 3. Реестр тикетов Phase 3

| Тикет | Заголовок | Тип | Статус | Суть выполненных работ |
|---|---|---|---|---|
| **01** | External config and Profiles | task | resolved | Вынесение настроек в TOML и Markdown, компиляция снапшотов, атомарная перезагрузка по SIGHUP и версионирование. |
| **02** | Event log and retention | task | resolved | Нормализация событий в SQLite, ротация сырых JSONL ACP-логов, очистка данных по истечении 30 дней / 1 GiB. |
| **03** | Server-owned MCP tools | task | resolved | stdio MCP bridge на каждую сессию, разделение прав между Secretary (lifecycle) и Worker (`spawn_subagent`), аудит вызовов. |
| **04** | Child worker tree | task | resolved | Персистентные Child Tasks, лимит до 4 детей на попытку, автозакрытие дочерних процессов, изоляция результатов от главной беседы. |
| **05** | OpenCode profile-first runtime | task | resolved | Нативная сессионная конфигурация OpenCode, передача профилей в ACP `_meta`, автоматическое одобрение permissions, resume snapshots. |
| **06** | Codex and fx compatibility runtimes | task | resolved | Адаптер совместимости для Codex (через `AGENTS.md`) и `fx` (через interrupt/idle/follow-up), явные ошибки при отсутствии рантайма. |
| **07** | Svelte mobile user UI | task | resolved | Разработка User UI на Svelte + Tailwind: авторизация, онбординг, диалоги, карточки воркеров, встроенная сборка в Go. |
| **08** | Svelte control room | task | resolved | Разработка инженерной панели `/control-room` под флагом `--debug`: дерево задач, события, сырые логи, редактирование конфигурации. |
| **09** | Product launcher and launchd | task | resolved | CLI `secretary`: управление службой через launchd (macOS), preflight-проверки, логи, doctor, передача токена через fragment. |
| **10** | Prove Phase 3 release gate | task | resolved / ready-for-human | Создание скрипта `scripts/phase3-release-gate.sh`, верификация Go тестов с флагом `-race`, проверка встроенных UI-ассетов и фиксация матрицы в `docs/phase3-release-gate.md`. |

## 4. Приёмочные доказательства (Release Gate)

1. **Автоматизированный гейт (`scripts/phase3-release-gate.sh`):**
   - Успешное прохождение `go test ./...` и `go test -race ./...` без состояний гонки.
   - Успешное выполнение `go vet ./...` и чистый `git diff --check`.
   - Проверка сборки статических ассетов: выполнение `npm ci && npm run build:all` для фронтенд-проектов и проверка корректности внедрения в бинарник через `embed.FS`.
   - Детерминированные тесты `internal/node/harness_compat_test.go` на эмуляторах подтвердили корректность логики для Codex, fx и OpenCode.

2. **Ручная матрица харнессов (`docs/phase3-release-gate.md`):**
   - Валидация цепочек `new` → `load` → `resume` → `prompt` → `cancel` на реальных локальных окружениях с установленными OpenCode, Codex и fx.
   - Проверка полного пользовательского пути: старт через `secretary start`, логин по ссылке, онбординг, запуск задачи, просмотр карточки воркера, генерация дочернего воркера, остановка задачи и корректное сохранение артефактов в `~/.local/share/secretary`.

## 5. Итоги и предпосылки для Phase 4

Phase 3 завершила формирование локального однопользовательского стека. Однако оставались ограничения:
- Привязка строго к одной локальной машине (невозможность делегировать тяжелую сборку на удаленный сервер).
- Перегруженность концепцией `Task`, которая смешивала намерение пользователя и процесс выполнения.
- Отсутствие мобильных мессенджеров (потребность в Telegram).

Эти вызовы определили переход к Phase 4 («One Secretary across machines»).
