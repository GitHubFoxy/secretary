# Research: Telegram multimodal input

Updated: 2026-10-11

## Summary

Vision is not a single switch shared by all models. The application must know whether the selected model supports image input and whether the selected harness can actually transport image content. An unknown capability must fail closed. This implementation should reject unsupported requests with the agreed `Can't do images` message rather than selecting a hidden fallback.

Telegram provides photo, document, video, and video-note message fields with downloadable file IDs. The standard cloud Bot API download limit is 20 MB. A 60-second video sampled once per second yields at most 60 frames under the agreed zero-based sampling policy; actual provider/model request limits remain harness-specific and image tokens still consume context. There is no useful provider-agnostic “images per request” number to configure as a promise.

Video processing needs two representations: timestamped sampled frames plus a timestamped transcript in model context, and the original video materialized in the Worker Workspace. It also needs an authenticated, bounded, replay-safe binary artifact transfer path across remote Execution nodes.

## Primary-source findings

### Telegram Bot API

- `Message` exposes `photo`, `document`, `video`, `video_note`, `voice`, and `caption`; `Video`/`VideoNote` include duration and file identity. A photo is represented as several `PhotoSize` variants, so select the largest available one for model input. An image sent as a document is a separate `Document` object and its downloaded bytes should be retained unchanged. File objects include `file_id`, optional `file_size`, and metadata. Use `file_id` with `getFile` to download; `file_unique_id` is not downloadable. See [Telegram Bot API: Message and media file objects](https://core.telegram.org/bots/api#message).
- The standard Bot API download maximum is 20 MB. A locally hosted Bot API server removes that limit, but deploying one is out of scope. See [Telegram Bot API: File](https://core.telegram.org/bots/api#file).
- File download links are guaranteed to remain valid for at least one hour and can be renewed with `getFile`. Durable replay should persist `file_id` and reacquire a URL instead of persisting a token-bearing download URL. See [Telegram Bot API: File](https://core.telegram.org/bots/api#file).

### Model image capability and request limits

- OpenAI's current Images and Vision API guide lists up to 1,500 images per request for the documented API input flow, alongside payload, patch and context constraints. This API ceiling does not establish what a chosen model or Codex harness accepts. Tokens and the rest of the prompt must fit model context. See [OpenAI Images and Vision: input requirements](https://developers.openai.com/api/docs/guides/images-vision#image-input-requirements).
- Anthropic currently documents 100 images/request for models with 200k context and 600 for other API models; request byte limits, image dimensions, model choice, and provider path can bind sooner. This is an example of provider/model-specific ceilings, not the Secretary limit. See [Claude vision: image limits](https://docs.anthropic.com/en/docs/build-with-claude/vision#request-limits).
- Gemini's video API uses static 1 FPS sampling by default, and the latest listed models also offer an agentic mode that adaptively changes inspection rate/resolution. The latter conflicts with the user's explicit preference for fixed, configured sampling and must not be used here. Its direct video upload size/context rules apply to Gemini API and are not a harness-neutral image count. See [Gemini video understanding](https://ai.google.dev/gemini-api/docs/video-understanding#agentic-video-understanding).
- Therefore do not add a generic provider maximum as the product contract. Use the configured video duration and FPS to bound generated frames, then preserve normal provider context/error behavior.

### ACP transport and compaction

- ACP represents an image as an `image` content block with required base64 `data` and `mimeType`; it also defines an optional `uri` reference. The agent must advertise the `image` prompt capability, and the client must constrain prompt content types according to negotiated capabilities. A URI alone is not documented as a portable replacement for `data`; validate any resource-reference behavior against the specific agent. See [ACP Content](https://agentclientprotocol.com/protocol/v1/content) and [ACP Prompt Turn](https://agentclientprotocol.com/protocol/v1/prompt-turn).
- ACP defines optional usage/compaction update notifications, but those do not themselves guarantee a given harness will compact before an over-limit prompt. The product requirement is harness-owned compaction; acceptance must verify it for each currently supported harness near capacity. Secretary should not implement compaction or silently shed video frames.
- OpenAI describes automatic compaction in Codex as part of its agent loop when the configured threshold is reached. This is evidence about Codex, not every harness. See [Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/).

### Video budget at the selected defaults

- `max_video_duration_seconds = 60`, `video_frames_per_second = 1` imply no more than 60 sampled frames when sampling times are `0, 1, …, duration-1`. This is an arithmetic consequence of the user-selected limits, not a provider guarantee.
- Audio is the full clip audio track and ASR output includes timestamps. Current local `ASRTranscriber` returns only a string. Current NeMo-Speech.cpp CLI docs state JSON/SRT/WebVTT output requests word timestamps automatically, so the likely minimal path is structured JSON and extending the wrapper to parse timed words. Verify the installed `nemo-speech` build/revision and selected Parakeet GGUF emit timestamps before relying on it. Do not synthesize timestamps from plain transcript text. See [NeMo-Speech.cpp CLI: structured output](https://github.com/NVIDIA/NeMo-Speech.cpp/blob/main/docs/cli.md#subtitles-and-structured-output).
- Telegram documents the cloud download ceiling as “20 MB” without specifying a byte conversion. The ticket chooses a stricter, explicit application cap of 20,000,000 bytes. Validate declared size before download and actual bytes while streaming; inspect decoded media and enforce duration. Telegram metadata alone is not a sufficient limit check.
- Telegram's `VideoNote` object has no `caption` field. Preserve captions only for message types where the Bot API supplies them; keep accompanying text and any recognized speech as separate content. See [Telegram Bot API: VideoNote](https://core.telegram.org/bots/api#videonote).
- A provider may reject image count or payload size before context capacity becomes relevant. Surface the runtime error without text-only retry, frame dropping, FPS reduction, or model fallback. Validate configured FPS against selected runtime limits and local processing bounds; reject unsupported values instead of silently clamping.
- Define fixed-rate samples as `n / fps` for integer `n >= 0` while the timestamp is strictly less than decoded duration. This excludes a frame at the duration endpoint and yields at most 60 frames for 60 seconds at 1 FPS. If a video has no audio stream, continue visual analysis without a transcript.

## Local codebase findings

- `internal/telegram/Message` and the Bot API DTO currently cover `Text` and `Voice` only. `deliverUpdate` has no photo/video branch. The Bot API transport already has `GetFile`/`DownloadFile`, reusable for media with a strict bounded-read implementation.
- Telegram persists pending updates before advancing its polling offset. Keep media identity in this durable path and do not ACK/forget an update before the data is safely staged or an explicit rejection is delivered.
- `internal/config/config.go` loads the main TOML config, while `internal/config/asr.go` reads an adjacent `config.yaml` sidecar currently used for ASR only. Per user direction, the feature must consolidate ASR into TOML `[asr]`, remove YAML loading/example, and put all new settings/model capabilities in TOML.
- The existing ASR interface (`internal/telegram/asr.go`) is `Transcribe(...) (string, error)`. Timestamped ASR requires changing/adding a structured result and validating actual `nemo-speech` output. The current upstream CLI documentation describes timed JSON output.
- `internal/node/acp_runtime.go` sends a single ACP text content block. It currently has no image prompt path. ACP session capabilities must be negotiated before sending image blocks.
- Secretary/Worker inputs, conversation entries, and Node dispatch are text-oriented. Worker tasks can run on remote Execution nodes; model context plus Worker Workspace file delivery crosses separate boundaries and both need durable identities.
- The current production cloud Bot API's 20 MB download maximum is documented by Telegram. User-approved feature cap is 20,000,000 bytes.

## Gemini cross-check and audit

Gemini 3.8 Flash Medium independently inspected the repository and wrote [its research report](research/gemini-research.md). It confirms the text-only Telegram/core/Node path, missing vision gate, caption handling, and the 60-second/1-FPS/full-audio pipeline decisions. I checked its implementation suggestions against current official sources before carrying any into the ticket.

Do not treat every detail in Gemini's report as a selected contract. It suggests specific `file:///` paths for some harnesses, a universal Claude auto-compaction threshold around 95%, strict-ACP URI transport, and estimates 60 frames at 4,000–16,000 tokens. These were not used: the current ACP Content page requires base64 `data` for an Image block and describes `uri` as an optional reference; actual runtime support must be negotiated and tested. ACP compaction reporting is optional and requires the client to advertise the feature. The 95% point is the user's desired scenario for harness acceptance, not a proven universal trigger. See the primary-source sections above.

One practical implication of the provider-specific image cost data: 60 frames are not guaranteed to be cheap. Claude's current API guide lists up to 1,568 visual tokens/image on standard models and 4,784 on high-resolution models, so a worst-case arithmetic budget for 60 frames would be about 94,080 or 287,040 visual tokens respectively, before text/audio and system context. These are provider/model upper-bound illustrations, not Secretary limits; a runtime may resize images differently or reject the request. The implementation must surface the selected runtime's normal context error if its own compaction cannot make room. See [Claude vision: resolution and token cost](https://docs.anthropic.com/en/docs/build-with-claude/vision#resolution-and-token-cost).

## Implementation decisions

The issue records accepted behavior and acceptance criteria. Key choices: Telegram only; images go to both Secretary and Worker; original files stay available to Worker tasks; explicit rejection/no vision fallback; 60-second configurable duration; 1 FPS configurable default; full audio with timed ASR; 20 MB Bot API ceiling; harness-owned compaction, with no dynamic FPS optimization.

## Agent-readiness audit (2026-10-12)

I checked the ticket against the current implementation seams. Telegram `botMessageDTO` and `Message` support text/voice only; `deliverUpdate` routes those two paths; `ServerClient` sends text strings. Core `SecretaryTurn.Input`, `Turn.Input`, `MessageWorkerRequest.Text`, and `WorkerEnvelope.OriginalUserIntent` are text-only, and `acpSession.promptTurn` sends one text block. There is no image capability in the existing harness capability contract. This means the work must extend the durable server-to-Node contract and the negotiated runtime prompt, not just Telegram parsing.

The ticket places media policy in TOML `[telegram.media]` and `model_capabilities` in root TOML tables, keyed by exact effective model ID; missing entry means unsupported. Secretary aliases resolve before lookup; an existing Worker's immutable binding determines its model. For a Worker media message, the server checks capability before queueing/steering, and Telegram only renders the typed rejection. Binary content remains in bounded artifact storage/transfer rather than JSON envelopes.

Other clarified fail-closed contracts: configured WebP encoding for model derivatives (quality 80 video, 85 stills by default); the original video is a separate Worker artifact; no use of ACP `uri` as a portable image substitute for required image `data`; deterministic context-pressure tests plus narrowly recorded live evidence; explicit decoder resource ceilings; and timestamped ASR parsing that errors visibly if the installed tool cannot return structured timestamps. The values for decoder safety ceilings are implementation constants to document and test, while the user-configured duration/FPS are never silently clamped.

Primary references checked for the ticket: [Telegram Message/media objects](https://core.telegram.org/bots/api#message), [Telegram File download limits](https://core.telegram.org/bots/api#file), [ACP Content](https://agentclientprotocol.com/protocol/v1/content), [ACP Prompt Turn capability negotiation](https://agentclientprotocol.com/protocol/v1/prompt-turn), and [NeMo-Speech.cpp structured timestamps](https://github.com/NVIDIA/NeMo-Speech.cpp/blob/main/docs/cli.md#subtitles-and-structured-output). Telegram confirms its cloud download ceiling as “20 MB”; the app's `20,000,000`-byte ceiling remains an explicit stricter application limit. ACP requires image `data` and `mimeType`; image prompt content is conditional on negotiated capability. NeMo's current CLI documentation says structured JSON/SRT/VTT output includes word timestamps; the installed build must still be checked at implementation time.

Implementation seam details: `internal/telegram/http.go` (`botMessageDTO`, `botUpdateDTO.update`, `BotAPITransport.GetUpdates/GetFile/DownloadFile`) owns Telegram decoding and download; `internal/telegram/adapter.go` (`processUpdate`, `deliverUpdate`, `deliverTextUpdate`) owns authorization and routing; `internal/telegram/input_queue.go` (`enqueueInputs`, `drainLane`) persists updates before advancing the polling offset and preserves per-topic order. `HTTPServerClient.SendMessage` and `SendWorkerMessage` in `internal/telegram/http.go` currently serialize text-only requests. Extend the main TOML typed config with `model_capabilities` and media policy; move existing ASR config into TOML and retire the YAML sidecar with an actionable legacy-file migration error. Durable recipient seams are `SecretaryTurn.Input` / `QueueSecretaryInput` (`internal/core/secretary_types.go`, `internal/core/secretary_api.go`), `MessageWorkerRequest.Text` (`internal/ctl/worker_lifecycle.go`), `WorkerEnvelope.OriginalUserIntent` (`internal/node/protocol_types.go`), and `StartRequest.Task` (`internal/node/node.go`). The prompt conversion seam is `acpSession.promptTurn` in `internal/node/acp_runtime.go`; remote Node frames are authenticated JSON (`Envelope` in `internal/node/protocol_types.go`), so attachments need a bounded artifact-transfer contract instead of embedding bytes in command envelopes. The ASR interface is `ASRTranscriber.Transcribe(...) (string, error)` in `internal/telegram/asr.go`; timed output requires a structured result. Telegram's [File object](https://core.telegram.org/bots/api#file) also documents that file sizes can exceed 32-bit integers, so media sizes must remain `int64`.


## Model-copy format, quality, and token cost

- The agreed defaults are WebP quality 85 for still-image model copies and WebP quality 80 for sampled video frames. Defaults cap the long side at 2048 px for still images and 1280 px for video frames. Originals remain unchanged for Worker artifacts. All output formats, quality values, and dimension caps are configurable in `[telegram.media]` in `config.toml`.
- OpenAI, Anthropic, and Gemini vision API docs list WebP as a supported image input format: [OpenAI image input requirements](https://developers.openai.com/api/docs/guides/images-vision#image-input-requirements), [Anthropic vision](https://docs.anthropic.com/en/docs/build-with-claude/vision), [Gemini image input](https://ai.google.dev/gemini-api/docs/image-understanding#supported-image-formats). The specific selected harness must still be checked.
- WebP lossy quality primarily changes encoded byte size and transfer time (encoding itself costs CPU); model image-token cost is principally driven by the dimensions/detail level the runtime actually processes. Resolution caps therefore provide the direct application-side token bound. Provider-specific resizing/detail settings may further alter cost; do not claim a universal token saving from quality 80/85 alone.
