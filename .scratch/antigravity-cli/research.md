# Research: Antigravity CLI harness

Дата проверки: 2026-10-12. Вопрос: как подключить Google Antigravity CLI как coding-agent harness в `secretary-v2`, отдельно от IDE extensions.

## Вывод

Поддерживаемый Google CLI существует: `agy`. Для автоматизированного запуска Google документирует headless/print режим (`agy -p`) с текстовым, JSON и NDJSON streaming вводом/выводом. Кроме того, Google публикует отдельный нативный ACP server — `agy_acp_server` — в официальной записи Antigravity ACP Registry. В проекте уже есть ACP transport и общий `ACPRuntime`, переводящий ACP в контракт Secretary. Минимальная архитектура — отдельный Antigravity runtime/compatibility adapter вокруг общего ACP runtime: он изолирует запуск, auth profile, resume/config и native request semantics, без второго JSON-RPC transport или универсального переводчика.

## Что подтверждают первичные источники

### CLI и headless API

- Google описывает Antigravity CLI как terminal surface общего agent harness Antigravity, а не IDE-only плагин: [CLI overview](https://antigravity.google/docs/cli/overview), [Google announcement](https://antigravity.google/blog/introducing-google-antigravity-cli).
- Для программного использования документирован headless режим: `agy -p/--print/--prompt`, JSON envelope или NDJSON `stream-json`, чтение нескольких prompts из stdin одним процессом. Это официальный CLI integration API на уровне процесса и pipe, но не ACP-метод: [Headless mode](https://antigravity.google/docs/cli/headless).
- Headless JSON включает `conversation_id`, `status`, `response`, `error`, `duration_seconds`, `num_turns`, usage и optional structured output. Streaming выдаёт `init`, `step_update`, `result`; step updates могут содержать text deltas, tool details и subagent info. Работа в папке определяется рабочей директорией процесса (`cwd` указан в `init`); флаг `--conversation` продолжает сохранённую беседу.
- Headless режим требует предварительно авторизованную CLI-сессию. По умолчанию действия, которым нужна интерактивная авторизация, soft-deny: агент может вернуть exit code 0, поэтому интеграция должна проверять поле `status`, а не только exit code. Для shell требуется подходящее локальное permission policy или широкий флаг `--dangerously-skip-permissions`; последний не следует включать автоматически. Те же ограничения описаны в [официальном руководстве headless](https://antigravity.google/docs/cli/headless).

### Нативный ACP

- В официальном [Antigravity CLI repo](https://github.com/google-antigravity/antigravity-cli) README указывает официальные документы CLI, а официальный [гайд Google для Zed](https://antigravity.google/docs/ide/extensions/zed) говорит установить Antigravity из ACP Registry. Здесь Zed — только подтверждение распространения ACP-компонента; предлагаемая интеграция Secretary использует ACP напрямую и не зависит от IDE.
- Запись [Google Antigravity в официальном ACP Registry](https://github.com/agentclientprotocol/registry/blob/main/antigravity-acp/agent.json) называет продукт `Google Antigravity`, автора `Google LLC`, лицензию `proprietary`, и публикует platform-specific ZIP с бинарником `agy_acp_server.par` (macOS/Linux) или `agy_acp_server.exe` (Windows). На дату проверки запись имеет version `1.3.0`, URLs ведут на домен Google `dl.google.com`. То есть для реализации следует использовать именно этот зарегистрированный executable, а не сторонний ACP bridge.
- Это отдельный ACP server binary из registry, не подкоманда `agy`. В установленном окружении `agy --version` вернул `1.3.3`; `agy --help` показывает headless CLI flags и не перечисляет ACP subcommand. `~/.local/bin/agy` и `~/.gemini/antigravity-cli/` присутствуют. Следов уже добавленного Antigravity harness в исходниках проекта не найдено.
- Я не нашёл у Google публичного источника, обещающего ACP server совместимость со всеми ACP extensions или гарантирующего полный набор lifecycle методов. Registry подтверждает доставку агента; перед включением capabilities нужно провести локальный handshake и проверить конкретные запросы. Не считать наличие registry-записи достаточным доказательством steering, cancel, resume, permissions, user-input, MCP и model/reasoning catalog.

## Следы и точки подключения в `secretary-v2`

- В проекте реализован `Runtime.Start` → `Session` контракт в [internal/node/node.go](../../internal/node/node.go): prompt, steer, cancel, activity/result, close, а для восстановления — optional `Resumer`.
- [internal/node/acp_runtime.go](../../internal/node/acp_runtime.go) реализует общий ACP lifecycle, session prompt, activity mapping, pending requests, управление и восстановление сессий. Минимальная граница: `internal/acp.Client` остаётся JSON-RPC transport; `ACPRuntime`/`acpSession` переводят общий ACP в Secretary `Runtime`/`Session`/`Activity`/`Result`; отдельный `AntigravityRuntime` по образцу `CodexRuntime` задаёт provider-specific запуск и узкие ACP compatibility behaviors. Сохранить identity `antigravity`, не использовать `CodexRuntime` и его `CODEX_CONFIG` environment.
- Для маршрутизации новый kind придётся добавить в [internal/core/harness_contract.go](../../internal/core/harness_contract.go), route в [internal/node/runtime_router.go](../../internal/node/runtime_router.go), discovery/probe в [internal/node/harness_probe.go](../../internal/node/harness_probe.go), а также в валидаторы конфигурации (`internal/config/config.go`). Сейчас известные kinds только `claude_code`, `codex`, `fx`, `opencode`.
- `HarnessProbeSpec` строится вокруг команд версии/auth/models/reasoning. Для `agy_acp_server` эти методы не подтверждены CLI help. Нужно определить probe по документации/протоколу либо честно ограничить первую ready-политику: наличие бинарника, его версия/registry release, авторизованный ACP initialize и наблюдаемый model/capability набор. Не объявлять `ready` по одному наличию бинарника.
- Registry определяет версию и platform artifact, но в изученном JSON нет SHA-256 digest. Если бинарник ставится/обновляется приложением автоматически, способ проверки целостности остаётся открытым. Более безопасный первый контракт — использовать системно установленный путь/явный конфиг и сообщать missing/unavailable; либо скачать только с опубликованных Google `dl.google.com` URLs с проверкой доверенного checksum, если его можно получить из официального источника.

## Рекомендация для тикета реализации

1. Добавить отдельный `antigravity` HarnessKind, discovery, конфигурационную селекцию и runtime routing.
2. Использовать официальный ACP registry artifact `agy_acp_server`, а внутри — существующий Go ACP transport, если smoke-probe проходит. Не подключать IDE extension и не писать сторонний ACP translation layer.
3. ACP config catalog не запрашивается отдельным `session/config_options` RPC. Стандарт передаёт `configOptions` в ответах setup/resume; клиент меняет вариант через `session/set_config_option`, а агент сообщает об изменениях полным `config_option_update` внутри `session/update`. Secretary сейчас сохраняет только `sessionId` из `session/new` и не обрабатывает `config_option_update`; generic option parsing ограничен плоской структурой. Нужно расширить наблюдение и проверку model/mode/reasoning options Antigravity, включая grouped/dependent options. См. [ACP Session Config Options](https://agentclientprotocol.com/protocol/v1/session-config-options).
4. T3 использует `session/resume`, а текущая Secretary `Resume` отправляет `session/load`. ACP различает `sessionCapabilities.resume` и `sessionCapabilities.loadSession`; `resume` не проигрывает историю, `load` загружает её. Выбор метода должен идти из объявленных Google capabilities и проверяться после закрытия процесса с восстановлением той же беседы, pins и MCP. Существующие harness сохраняют прежнее поведение. См. [ACP session/resume](https://agentclientprotocol.com/rfds/session-resume).
5. До готовности реализации определить Antigravity auth flow. T3 вызывает ACP `authenticate` до открытия сессии, использует стабильный профиль на provider instance и отдельно распознаёт login URL в stdout/stderr. Secretary `ACPRuntime.connect` пока лишь инициализирует протокол; не-JSON login URL может потеряться в Go ACP reader. Поддержать документированный ACP auth method/profile или быстро сообщать, что требуется интерактивный login; не читать токены и не выводить готовность из `agy` auth.
6. Добавить Antigravity-specific классификацию native questions. T3 распознаёт `interaction_*` options в `session/request_permission` как вопрос, тогда как текущий Secretary общий handler считает такой запрос permission и отвечает allow/reject. В адаптере сохранить native option IDs, правильно разделять approval и user input; неизвестные ответы не подтверждать автоматической approval policy.
7. Уточнить launch artifacts: T3 требует companion `localharness_external` рядом с `agy_acp_server`, выставляет `ANTIGRAVITY_HARNESS_PATH` и разрешает symlink до поиска соседа. В первой версии не скачивать артефакты, но проверять пару и строить команду из официальной ACP Registry записи для платформы.
8. Учесть, что daemon обновляет inventory каждые 5 минут. Не запускать тяжёлый Antigravity bundle/session при каждом refresh; кэшировать дорогие handshake/auth/catalog observations с явной инвалидацией. Сейчас discovery теряет `ProbeResult.ErrorCode` и ошибку при построении snapshot, а `HarnessInstance` не несёт причину unavailable: передавать безопасную диагностику через inventory или равнозначный операторский канал.

## Сверка с реализацией T3 Code

Источники ниже — исходный код другого продукта, а не контракт Google. Он полезен как проверенный интеграционный пример и показывает, какие работы возникают за пределами минимального runtime.

- T3 использует именно официальный `agy_acp_server` из ACP Registry, а не запускает интерактивный `agy` и не оборачивает `agy -p`. В [AntigravityAdapterV2](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/orchestration-v2/Adapters/AntigravityAdapterV2.ts) создаётся flavor общего ACP adapter, а [AntigravityAcpSupport](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/acp/AntigravityAcpSupport.ts) настраивает общий `AcpSessionRuntime`. В [AntigravityDriver](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/Drivers/AntigravityDriver.ts) создаётся runtime, а [antigravityAuthSupport](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/antigravityAuthSupport.ts) строит subprocess command/env/cwd. Этот пример подтверждает, что прямой ACP — рабочий путь интеграции.
- Поток общения идёт по ACP поверх stdio через общий T3 `AcpSessionRuntime`: `session/new`/prompt/events и resume; flavor ставит `preferResumeSession: true` ([adapter source](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/orchestration-v2/Adapters/AntigravityAdapterV2.ts)). Историю при cold load T3 предпочитает resume, поскольку ACP load повторно проигрывает все tool calls — это пояснено комментарием в source. ACP protocol normalization делается отдельно в [AntigravityProtocol](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/acp/AntigravityProtocol.ts).
- T3 не использует `agy models` для выбора модели в этом provider. Общий T3 ACP runtime хранит config options, полученные из session setup/resume и `config_option_update`; Antigravity support читает этот локальный каталог, проверяет явный model pin и меняет option через общий `session/set_config_option` путь ([AcpSessionRuntime](https://github.com/pingdotgg/t3code/blob/f23d0084b6e023ffb1af9e332d8666affc99d542/packages/provider-acp/src/server/AcpSessionRuntime.ts#L2239), [AntigravityAcpSupport](https://github.com/pingdotgg/t3code/blob/f23d0084b6e023ffb1af9e332d8666affc99d542/apps/server/src/provider/acp/AntigravityAcpSupport.ts)). Отдельного ACP `session/config_options` RPC нет.
- Права/approval проходят через ACP. `sessionModeForPolicy` переводит режимы T3 в нативные значения `yolo`, `auto_edit`, `default`; на permission prompt mapping разрешает только варианты, которые реально прислал агент (`allow_once`, `allow_always`, `reject_once`), а `interaction_*` обрабатывает как user-input question, не approval ([ACP support](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/acp/AntigravityAcpSupport.ts), [protocol normalization](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/acp/AntigravityProtocol.ts)). Secretary должен сохранять received ACP option IDs и не синтезировать неподдержанные действия.
- Файловые чтение/запись T3 в chat flow проводит через ACP client `fs.readTextFile`/`fs.writeTextFile`, ограничивая доступ workspace + attachments и проверяя symlink/path containment ([AntigravityClientFiles](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/acp/AntigravityClientFiles.ts), [ACP adapter flavor](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/orchestration-v2/Adapters/AntigravityAdapterV2.ts)). В Secretary существующий ACP runtime и `WorkerEnvelope.Workspace`/MCP seam уже дают другой путь; это не означает, что Worker должен включить ACP filesystem capabilities.
- MCP: setup и model-catalog runtimes у T3 явно запускаются с `mcpServers: []`; связанные потоки проходят через общий ACP runtime. Открытая T3 discussion указывает, что текущий ACP adapter тогда передаёт только свой служебный `t3-code` MCP, не пользовательский список; workaround с `mcp_config.json` в provider profile — специфичная для T3 деталь и нестабильный opaque path ([discussion #13117](https://github.com/pingdotgg/t3code/discussions/13117)). В Secretary правильнее передавать уже имеющийся `StartRequest.MCPServers` через существующий ACP `session/new` механизм и отдельно проверить, что Google server их принимает.
- Бинарник поставляется вместе с `localharness_external`/`localharness_external.exe`; T3 считает оба файла обязательной парой. Он держит аккаунты Antigravity изолированными по provider instance отдельными профилями, готовит `settings.json`, чистит ambient Google credentials и разделяет temp dir на процесс ([installation](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/AntigravityInstallation.ts), [auth/profile/spawn](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/antigravityAuthSupport.ts)). Документация T3 прямо говорит, что ACP agent имеет отдельный sign-in от Antigravity IDE и CLI ([provider guide](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-antigravity.md)). Это важное отличие: наличие авторизованного `agy` не доказывает, что ACP server уже авторизован.
- У Registry manifest нет digest, но T3 реализует pinned release catalog: [antigravityRelease.ts](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/antigravityRelease.ts) хранит release version, URLs, sizes и SHA-256; [installer](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/AntigravityInstallation.ts) валидирует скачанный archive и оба распакованных бинарника и сохраняет versioned release, не меняя файлы активного процесса. Для Secretary это пример надёжного managed install, но он существенно шире минимального harness ticket; если scope не включает installer/update, оставлять бинарник под системным управлением/явным path — меньшая первая задача.
- T3 отдельно предупреждает, что bundled server — крупный PyInstaller binary (несколько сотен MB compressed, порядка гигабайта распаковывается в runtime temp); его driver не запускает его на частом health probe, а только резолвит установленную версию. См. комментарии и probe в [AntigravityDriver](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/provider/Drivers/AntigravityDriver.ts). Для Secretary probe также не должен создавать ACP session только ради частого readiness check.

### Несовпадения T3 Code и Secretary

- T3 строит multi-account provider subsystem: auth flow, отдельные профили Google, browser callback relay, model catalog refresh, runtime installer/update/remove, usage probing, UI permission modes и ACP session persistence. Secretary discovery сегодня описывает один локальный `HarnessInstance` на Node+kind, с capability/model observations и выбранным runtime; не переносить всю T3 provider architecture в минимальный ticket.
- В T3 ACP runtime создан на TypeScript `effect-acp`/внутреннем `AcpSessionRuntime`; здесь уже есть собственный Go ACP client (`internal/acp`) и ACP-compatible `ACPRuntime`. Не переносить TS-зависимости и новый protocol library.
- T3 использует `session/resume` для продолжения native conversation и свои механизмы профиля/credential isolation. Текущий Go ACP runtime в Secretary при `Resume` посылает `session/load`; этот method mismatch критичен. Перед реализацией проверь, какой метод объявляет/поддерживает Google server. Если он требует `session/resume`, расширить существующий ACP transport/runtime на capability-based resume вместо безусловного load, не считать generic ACP-поддержку автоматической совместимостью.
- Текущая Secretary discovery обновляется каждые пять минут, но ACP probe требует больше, чем CLI version check: initialize/auth/session setup. Не создавать полный сервер и временную session на каждом таком refresh; кешировать дорогое наблюдение и сохранять пригодную диагностику. В `HarnessProbe.Discover` сейчас теряются ошибки отдельных `ProbeResult`, а `HarnessInstance` не содержит причины состояния.
- Общий ACP request handler Secretary считает `session/request_permission` approval, а T3 provider-specific normalizer различает `interaction_*` вопросы и permission options. Переиспользовать handler без этой проверки небезопасно для корректности: Антигравити-вопрос нельзя сводить к allow/reject.
- `ExecutionNode.watchSession` закрывает процесс при Outcome только для OpenCode, Claude и Codex; добавление нового процесса требует отдельно проверить и учесть graceful close/cleanup для Antigravity.
- T3 может выставлять собственные permission modes, account setup и custom auth methods (Google account, Gemini Enterprise/API key/Agent Platform). Текущая конфигурация Secretary хранит harness/model/reasoning pins, но не multi-account profiles и не auth flow. Для первой задачи выбрать scope авторизации явно; минимум — подключение уже авторизованного ACP registry server/учётки, без автоматического управления аккаунтами.
- T3 умеет native file system permissions и MCP discovery / provider-specific compatibility. В Secretary ACP request handlers уже нормализуют permission/input activities и есть Worker-specific MCP injection; но конкретный набор запросов Antigravity необходимо подтвердить real server'ом.
- T3 registry release/hash map pinned в его собственной версии и может отставать от current Registry; не копировать его номера версий/digests как вечные или достоверные значения для Secretary. Для установки скачать manifest/asset из доверенного Google URL и проверить release-specific digest, если артефакт его публикует; отсутствие digest должно быть явным решением тикета.

## Неизвестные факты и обязательные проверки

- Для Registry artifact `1.3.0` локальный initialize подтверждён ниже; при поддержке других версий всё равно нужно проверять объявленные ими capabilities, а не считать их одинаковыми.
- Доступны ли в ACP server `session/load`, cancel, same-turn steering, durable permission requests/responses, `user_input_request`, MCP config, managed system instructions, и какие модели/effort доступны для каждого auth method.
- Какая CLI/auth команда документированно наблюдает credential state для ACP server без чтения секретов; какие permissions нужны в `~/.gemini/antigravity-acp/settings.json` и как пользователь авторизует сервер вне Zed.
- Кто отвечает за загрузку/обновление официального ACP binary в этом продукте и как проверять целостность: в Registry manifest, который я просмотрел, нет digest.
- Полная поддержка Antigravity CLI и ACP artifact на всех платформах: Registry публикует macOS/Linux/Windows варианты, но runtime-интеграция проекта должна отдельно учитывать текущую платформу Node и особенности запуска бинарника.
- Совместимость конкретной версии ACP server с используемой в repo ACP protocol version и расширениями Secretary; нужна real-harness acceptance, а не только fixture tests.

## Итоги независимого design review
