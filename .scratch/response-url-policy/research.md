# Исследование политики URL в ответах

## Краткий вывод

Минимальный безопасный путь состоит из двух частей: закрепить смысловое правило в профилях Secretary и Worker, а Telegram попросить отключать link preview для их ответов. Не следует глобально вырезать URL из произвольного текста: это может повредить код, исходные данные и запрошенные технические материалы, что прямо запрещено границами spec.

Текущий formatter уже отображает обычный безопасный Markdown-link как кликабельный HTML `<a href>` с названием вместо адреса. Но Bot API сейчас не получает параметр отключения preview. Ещё два существенных исключения требуют решения: при parse fallback plain text содержит сырой URL, а ссылка, не помещающаяся в один chunk, может быть отправлена как обычный escaped-текст.

Для внешних профилей одного изменения embedded defaults недостаточно. Предыдущий репозиторный production report фиксирует custom paths для Secretary и Worker; я не проверял их live-состояние и не трогал production. Живую проверку acceptance в рамках этого исследования не проводил.

## Подтверждённые факты с источниками

- Issue и spec требуют не показывать URL по умолчанию, включая citations/source links; при явном запросе выдавать Markdown-link с коротким названием, сохраняя проверку источников и честное описание неопределённости. Правило должно быть в профилях, а не в повторяющемся Task prompt. История и необходимые URL в технических материалах вне scope автоматического удаления. (`.scratch/response-url-policy/issues/01-omit-unrequested-urls.md:1-22`; `.scratch/response-url-policy/spec.md:1-21`.)
- Embedded Secretary profile задаёт идентичность и обычный путь ответа/делегирования, но не содержит политики URL. Embedded Worker profile просит вернуть «any essential evidence or source» и требует не выдумывать факты и проверять актуальные источники. Это можно уточнить, не ослабляя проверку и отчёт об ограничениях. (`internal/config/defaults/secretary.md:1-5`; `internal/config/defaults/worker.md:1`.)
- Default config указывает профили как `profiles/secretary.md` и `profiles/worker.md`. `config.Load` разрешает относительный путь от каталога `config.toml`, а абсолютный путь оставляет абсолютным. `ensureDefault` копирует defaults только при отсутствии самого config-файла; существующие внешние профили автоматически не заменяются. (`internal/config/defaults/config.toml:1-6`; `internal/config/config.go:136-214`; `internal/config/manager.go:72-96`.)
- `secretaryd` по умолчанию читает config из `<dataDir>/config.toml`, затем компилирует его profiles. Secretary получает профиль из активного snapshot; Worker service читает compiled Worker profile при создании Worker. Worker profile сериализуется в durable snapshot binding, поэтому обновление внешнего профиля не переписывает существующие Worker bindings. (`cmd/secretaryd/main.go:110-120, 267-270, 303-310, 730-779`; `internal/ctl/worker_lifecycle.go:399-415`; `docs/architecture/runtime-contracts.md`, разделы «Короткое подтверждение перед работой» и «Worker profile и Dispatch».)
- В прежней production evidence записаны custom paths `profiles/secretary-codex-phase5.md` и `profiles/worker-template-luna6-low-9e3-v1.md`; карта отдельно говорит, что их надо обновлять явно. Это репозиторная запись о предыдущем deployment, не подтверждение текущей конфигурации. (`.scratch/secretary-response-style/map.md:8-13`; `.scratch/secretary-response-style/report.md:34-39`.)
- Telegram путь Secretary буферизует delta/final, применяет `safeText`, собирает сообщение в `Flush` и отправляет через `sendMessage`. Terminal Worker Result также проходит через `safeText`, отправляется в Worker topic, а затем зеркалируется в General; все эти сообщения используют тот же outbox и chunk delivery. (`internal/telegram/adapter.go:721-853, 904-1008, 1120-1255`; runtime contract, раздел «Conversations и доставка сообщений».)
- `formatTelegramChunk` переводит поддерживаемый Markdown в ограниченный HTML и экранирует обычный текст. `telegramInline` превращает безопасный `[label](URL)` в `<a href="URL">label</a>`; разрешены абсолютные `http`/`https` без credentials, пробелов и control characters. Обычное отображаемое содержимое HTML-link — только label. (`internal/telegram/format.go:17-57, 64-139`.)
- Plain fallback устроен иначе: для валидного Markdown-link он записывает `label (URL)`. Существующий тест явно фиксирует это поведение. В тесте parse rejection адаптер сохраняет fallback в outbox и повторяет отправку без `parse_mode`; тест проверяет, что URL остаётся в отправленном plain text. (`internal/telegram/format.go:64-91`; `internal/telegram/format_test.go:16-32, 55-107`.)
- Разбиение выполняется до форматирования, ориентируется на UTF-16/grapheme boundaries и старается не пересекать Markdown-link atom. Если атом слишком велик для одного chunk, он может быть разделён и уйти как читаемый escaped-текст, а не как кликабельный link. Это поведение зафиксировано тестом для oversized Markdown atoms. (`internal/telegram/adapter.go:1170-1255, 1295-1368, 1410-1499`; `internal/telegram/long_message_delivery_test.go:173-196`.)
- `OutgoingMessage` содержит `ParseMode`, но поля preview нет. `BotAPITransport.SendMessage` передаёт `chat_id`, `text`, необязательный `parse_mode` и `message_thread_id`; link preview option сейчас не отправляется. (`internal/telegram/adapter.go:48-55`; `internal/telegram/http.go:147-155`; `internal/telegram/http_test.go:20-43`.)
- Официальная документация Telegram Bot API описывает `link_preview_options` у `sendMessage` и `LinkPreviewOptions.is_disabled`. Официальный changelog говорит, что `link_preview_options` заменил `disable_web_page_preview`. HTML-style formatting поддерживает inline links. Ссылки проверены в документации Telegram: [sendMessage](https://core.telegram.org/bots/api#sendmessage), [LinkPreviewOptions](https://core.telegram.org/bots/api#linkpreviewoptions), [Bot API changelog](https://core.telegram.org/bots/api-changelog), [HTML-style formatting](https://core.telegram.org/bots/api#html-style).
- Существующие Telegram tests уже проверяют HTML escaping, safe/unsafe URLs, баланс HTML при chunk boundaries, parsed UTF-16 limit, parse-error-only retry и durable outbox recovery. Они пока не проверяют `link_preview_options` и требуемое отсутствие сырого URL в fallback. (`internal/telegram/format_test.go:16-145`; `internal/telegram/long_message_delivery_test.go:158-196`; `internal/telegram/http_test.go:20-43`.)
- `docs/adr/` не содержит ADR-файлов, поэтому выявленного ADR-конфликта нет.

## Гипотезы и неопределённость

- Profile instruction уменьшит нежелательные URL, но не создаёт runtime-гарантию: модель всё ещё может вывести raw URL или citation. Из репозитория не видно сигнала, который надёжно различал бы «пользователь явно запросил ссылку» и «модель сама решила её добавить».
- Отключать preview только по найденному Markdown-link можно, но такой способ не покрывает raw URL и malformed/oversized Markdown. Передавать признак на уровне источника ответа проще и предсказуемее; это означает выключать preview и у ответов без ссылок, где настройка не даст видимого эффекта.
- Успешный HTML путь показывает label как кликабельную ссылку без видимого URL. При отказе HTML текущий fallback показывает URL. Если заменить его на label-only, сырой URL пропадёт, но ссылка в fallback станет некликабельной. Гарантировать кликабельность и при отказе HTML, вероятно, потребует отдельного Bot API entities пути; в текущем коде его нет.
- Для слишком длинного URL-bearing Markdown атома текущий splitter выбирает lossless escaped text вместо неполного HTML. Нужно решить, остаётся ли приоритет сохранности source-текста или acceptance требует отдельной обработки такого аномально длинного линка.
- Указанные external production profile paths основаны на ранее сохранённом report, а не на текущем чтении live config. Их актуальность не подтверждена.

## Варианты и рекомендуемый минимальный подход

1. **Только профили.** Добавить правило в embedded Secretary и Worker profiles; заменить требование Worker «essential evidence or source» на сохранение доказательной основы без URL, если пользователь не просил ссылку. Оставить проверку источников, uncertainty и ограничения. Это минимально, но не управляет Telegram preview и не гарантирует соблюдение моделью.
2. **Профили плюс узкое управление preview, рекомендуется.** Добавить необязательный preview-флаг к `OutgoingMessage` и сериализовать официальный `link_preview_options` с `is_disabled: true`. Выставлять его на исходящих пользовательских ответах Secretary и Worker Result (включая General mirror и все chunks), а не на task prompts и зеркалах входных сообщений. Передавать настройку также при parse fallback и восстановлении outbox. Не удалять URL из содержимого общего sanitizer.
3. **Фильтр или глобальная перепись URL.** Отклонить: URL могут быть частью кода, исходного ввода и необходимых технических материалов; это противоречит границам spec. Кроме того, фильтр не может безопасно определить по строке, запросил ли ссылку пользователь.

Для варианта 2 отдельно зафиксировать политику parse fallback. Нынешний `label (URL)` несовместим с требованием никогда не показывать raw URL для запрошенной ссылки. Минимум для no-raw — fallback выводит только label, принимая потерю кликабельности в редком случае HTML parse rejection. Если кликабельность обязательна и в этом отказном пути, нужен отдельный entities fallback и дополнительная проверка; это уже не минимальное изменение.

Изменения defaults должны быть применены к реально настроенным внешним Secretary/Worker profile files отдельным контролируемым обновлением. Нельзя рассчитывать, что `config.Open` перепишет их; новые Worker snapshots будут использовать новую версию после reload, существующие bindings останутся прежними. Текущий production path перед таким обновлением надо подтвердить отдельно, не полагаясь только на старый report.

## План проверки

1. Тесты профилей: Secretary и Worker запрещают незапрошенные raw/Markdown URLs, но явно сохраняют поиск, проверку и сверку источников, неопределённость и точный отчёт об ограничениях. Проверить, что boilerplate не добавился в Task prompt и workspace `AGENTS.md`.
2. Config/profile тесты: custom relative и absolute profile paths компилируются; reload меняет активный snapshot для новых Workers, но не изменяет сохранённый snapshot существующего Worker.
3. Formatter тесты: запрошенный `[короткое название](https://...)` даёт корректный `<a href>` с label в visible text; unsafe schemes не становятся link. Добавить boundary cases для URL рядом с лимитом и слишком длинного Markdown atom.
4. Bot API HTTP fixture: проверить сериализацию `link_preview_options` с `is_disabled: true` для ответа Secretary, Worker topic, General mirror и каждого chunk; проверить, что флаг сохраняется при parse fallback и outbox restart. Зафиксировать выбранное fallback-поведение без сырого URL.
5. Regression для текста без ссылки и исходного Task prompt: содержание остаётся неизменным; не вводить глобальную URL-замену. Повторно проверить parse-error-only retry, dedup и UTF-16 splitting.
6. После утверждённого rollout выполнить живую проверку двух вариантов в Telegram: обычный результат с использованными источниками, но без URL; отдельно ответ на явный запрос короткой Markdown-ссылки без preview. Это исследование не проводило таких отправок и не меняло production.

## Открытые вопросы

- Отключать preview на всех финальных ответах Secretary/Worker или только если в ответе есть ссылка? У runtime нет явного поля «ссылка была запрошена».
- Что важнее при Telegram parse rejection: строгий запрет видимого raw URL или кликабельность ссылок? Нужен выбор между label-only plain fallback и дополнительной поддержкой entities.
- Какой fallback ожидается для слишком длинного URL-link, который нельзя сохранить как один HTML atom в лимите Telegram?
- Нужно ли применять правило к `child_worker` profile? Spec задаёт Secretary и Worker; runtime contract говорит, что Child Results возвращаются родительскому Worker, а не непосредственно в Personal Conversation.
- Какие external profile paths действуют сейчас и какой контролируемый reload/restart требуется, чтобы новая политика вступила в силу у Secretary и новых Workers? Production не инспектировался в рамках этого исследования.
