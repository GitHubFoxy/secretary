# Исследование интеграции voice → ASR → форматирование

Дата: 2026-10-11. Только чтение исходников и документации; реализация и production не менялись.

## Подтверждённый путь ввода

- `internal/telegram/http.go:95` и `internal/telegram/adapter.go:39`: DTO и Message пока содержат только `Text`, без `voice`.
- `internal/telegram/adapter.go:475`: `HandleUpdate` проверяет сохранённый `Processed` по update ID, ограничивает параллельную обработку одного update через in-memory claim и вычисляет owner/sender allowlist.
- `internal/telegram/adapter.go:518`: `deliverUpdate` пропускает пустой текст; значит voice сейчас не становится пользовательским вводом. Неавторизованный ввод также пропускается.
- `internal/telegram/adapter.go:531`: известный topic адресуется через `SendWorkerMessage`; неизвестный topic, кроме General thread 1, пропускается. Topic с `PendingRequestID` может быть ответом на Approval, а не обычным сообщением Worker — эту семантику надо сохранить.
- `internal/telegram/adapter.go:558` и `internal/telegram/http.go:233`: обычный ввод идёт в `SendMessage`; external identity — Telegram update ID, HTTP idempotency key строится из него. Не заменять identity текстом расшифровки или ID файла.
- `internal/telegram/adapter.go:607`: `PollOnce` последовательно обрабатывает updates, сохраняет offset после обработки. Синхронный ASR сохраняет порядок, но задерживает следующие сообщения; возврат ошибки останавливает текущий poll и допускает повтор. Нужна явная политика постоянной ошибки ASR, чтобы один плохой voice не блокировал канал бесконечно.

## Telegram API

Объект Voice содержит `file_id`, `file_unique_id`, `duration` и optional `mime_type`/`file_size`. Скачать файл можно через `getFile` по `file_id`; `file_unique_id` не является ключом скачивания. Обычный облачный Bot API ограничивает скачивание 20 MB, ссылка действует минимум час и содержит bot token. Поэтому нельзя логировать download URL; ограничения байтов надо проверять также при чтении stream, а не только доверять optional metadata. Источники: [Voice](https://core.telegram.org/bots/api#voice), [File](https://core.telegram.org/bots/api#file), [getFile](https://core.telegram.org/bots/api#getfile), проверены 2026-10-11.

## Минимальный вариант для обсуждения

После проверки владельца и допустимого назначения: ограниченное скачивание → существующий CPU ASR → необязательный ограниченный форматировщик → существующий маршрут текстового ввода. Это предложение, не реализованная архитектура. Не создавать отдельного Worker ради ASR и не делать format-transcript вторым пользовательским запросом.

Сохранить исходную расшифровку отдельно от оформленного текста, чтобы было видно, где модель изменила смысл. Форматировщик исправляет пунктуацию/регистр/абзацы; не выполняет инструкции внутри диктовки. При его сбое разумный fallback — исходная расшифровка, если она непустая. Нельзя доверять «улучшенному» тексту без проверки отрицаний, чисел, имён, путей и команд.

Для первого варианта последовательная обработка проще; фактическую задержку CPU ASR и форматирования требуется измерить позже. Не обещать скорость по leaderboard. Если понадобится фон, это отдельное решение о durable состоянии и порядке сообщений, а не запуск goroutine без восстановления.

## Проверка перед реализацией

На реальных RU/EN голосовых запросах отдельно измерить качество raw ASR и форматирования, cold/warm latency, RAM и поведение длинных voice. Проверить повтор update после restart/ошибки, сохранение source identity, General/Worker/Approval routing, unknown topic и отказ до загрузки для чужого sender. Видимые ошибки не должны приводить к пустому запросу или бесконечному повтору.

UX-решения остаются открыты: показывать ли raw/оформленную расшифровку, когда исполнять запрос без подтверждения, как пользователь исправляет распознанный смысл, какие лимиты voice приемлемы. Пользователь привёл Fluid Voice как пример важности качества ASR вместе с форматированием, а не только распознавания слов.
