# 23 Сквозной E2E: чистая машина, установка, CLI и реальные harness adapters

Type: task
Status: needs-triage
Related: 13b, 05b, 15

## Цель

Создать один воспроизводимый продуктовый E2E-прогон от чистой машины до проверенного Worker Result и восстановления после перезапуска. Прогон состоит из отдельных этапов с независимыми проверками, но имеет общий run ID и итоговый вердикт.

Агенты выполняют пользовательские действия. Runner проверяет наблюдаемые факты. Заявление агента об успехе не считается доказательством.

Связанные локальные тикеты:

- [26: Полный пользовательский путь](26-full-product-user-journey.md), перенесён из GitHub #3.
- [25: Prompt-driven E2E](25-prompt-driven-e2e-acceptance-suite.md), перенесён из GitHub #2.

Тикет дополняет Phase 4 ticket 15. Он не заменяет protocol/lifecycle gate и не закрывает его обязательные BLOCKED или NOT RUN по результатам другого теста.

## Исходное состояние

Текущий `./sex setup` собирает бинарники из исходников и проверяет уже настроенный harness. Это не установка готового релиза пользователем на чистой машине. Подмена HOME и fake ACP полезны для deterministic tests, но не доказывают установку, работу служб и настоящих harness adapters.

## Работа

### 1. Зафиксировать установочный контракт

- Описать установку готового релиза в `docs/install.md`, без приватных путей и недокументированных переменных.
- Зафиксировать документированную команду установки. `secretary.sh install` является примером, а не уже существующим интерфейсом. Не переименовывать исторический CLI `sex` без отдельного решения.
- Определить release manifest: версия, commit, платформа/архитектура, checksum и допустимые пределы размера бинарников.
- Если installer или release artifacts отсутствуют, оформить их как явные prerequisites. Не подменять установку готового релиза сборкой из source checkout внутри тестовой машины.

### 2. Подготовить чистую машину и runner

- Начать с Linux VM с systemd, новым пользователем и без состояния Secretary, harnesses и provider credentials.
- Каждый прогон начинает с чистого image/snapshot. Изоляция только через HOME недостаточна.
- Runner фиксирует версию VM image, целевой релиз/commit, версии агентов и их инструкции.
- Проверяемый релиз подготавливается вне VM. На машине установки агенту не выдаётся source checkout.
- Все изменения файлов и тестовые задачи ограничены этой VM и отдельным disposable Project.
- У каждого этапа есть deadline, наблюдаемые условия успеха и сохранённый отчёт. Ошибка обязательного этапа останавливает зависимые этапы.

### 3. Первый агент: установка по инструкции

Агент получает только чистую машину, `docs/install.md`, адрес зафиксированного релиза и терминал.

- Выполняет документированную установку как обычный пользователь.
- Не читает исходники, не чинит installer и не использует скрытые знания о репозитории.
- Недостаточная инструкция, неописанная зависимость или необходимость обходного пути фиксируются как ошибка продукта, а не как успешная установка.

Runner независимо проверяет:

- Наличие, исполнимость и ожидаемые пути установленных бинарников.
- Подходящую архитектуру, checksum, версию и commit.
- Размер относительно manifest, а не произвольного точного числа.
- PATH, права и расположение persistent state.
- Отсутствие ненамеренного изменения других пользовательских данных.

### 4. Второй агент: CLI установленного продукта

Второй агент получает ту же установленную VM и документацию CLI, но не историю рассуждений первого агента.

- Построить матрицу всех документированных команд и назначить каждой этап с нужными prerequisites.
- Проверить help, version, неизвестные команды, неверные аргументы, диагностику и настройку.
- Проверить запуск, status, логи с ограничением времени, остановку и повторный запуск.
- Проверить соответствующий платформе механизм установки службы и отсутствие второго процесса при повторном запуске.
- Node enrollment, revoke, удаление службы и остальные mutations проверять только после создания необходимых объектов, в безопасном порядке.

Runner проверяет exit codes, HTTP health, количество процессов и фактическое состояние системы. Текст вроде "started successfully" не заменяет эти проверки.

### 5. Установка harnesses и проверка каждого adapter

Для `fx`, Claude Code и Codex отдельно:

1. Установить harness и нужный ACP adapter по документации.
2. Проверить версии и выполнить поддерживаемую авторизацию.
3. Проверить observed inventory и готовность HarnessInstance на Node.
4. Явно выбрать этот harness при Dispatch, без fallback.
5. Выполнить настоящую задачу: создать файл с заданными байтами, изменить его и проверить результат.
6. Проверить activity, terminal AttemptOutcome, Result и соответствие выбранному binding.

- Credentials предоставляет runner через защищённое provisioning либо пользователь через официальный вход. Секреты не передаются в prompts и не публикуются в evidence.
- Отсутствие авторизации обязательного harness даёт BLOCKED, а не PASS или незаметный skip.
- Fake ACP и deterministic doubles не заменяют real adapter evidence.
- OpenCode проверяется отдельно как optional compatibility target.
- Первый рабочий вертикальный прогон можно построить с `fx`, затем расширить тот же runner на обязательную матрицу. Одного `fx` недостаточно для окончательного закрытия тикета.

### 6. Полный пользовательский путь

После установки и enrollment Node:

- Подключить Web через документированный owner flow и зарегистрировать disposable Project.
- Отправить задачу через клиент, а не напрямую вызвать WorkerService из теста.
- Проверить подтверждение делегирования, создание Worker и доступность Secretary, пока Worker выполняется.
- Проверить фактические файлы независимо от model prose и доставку одного terminal Result.
- Проверить, что progress не смешан с final Result, а переносы, списки и ссылки отображаются по клиентскому контракту.
- Направить Follow-up тому же Worker и проверить новый Turn без создания другого Worker.
- Перезапустить idle server и проверить сохранение Person, Conversation, Worker, Client session и восстановление Node connection без ручной правки базы.
- Повторная доставка Client request с тем же idempotency key не создаёт дубликаты работы.
- Проверить остановку, повторный запуск службы и сохранность истории.

Telegram-путь выполняется в отдельном тестовом чате при явно предоставленном bot/account provisioning: General → Worker Topic → progress → Result → Follow-up. Обычный пользовательский чат не используется как fixture. Если Telegram является обязательным этапом выбранного полного прогона, отсутствие provisioning оставляет его BLOCKED и не допускает общего PASS.

## Evidence и результат

Одна команда runner запускает весь выбранный сквозной прогон.

Артефакты одного run ID содержат:

- VM image, release version/commit/checksum и версии harnesses/adapters.
- Этап, документированные команды, временные отметки, exit codes и независимые assertions.
- Безопасную корреляцию Client request → Secretary turn → Worker/Turn/Attempt → Result → delivery.
- Ожидаемые и фактические файловые результаты, количество процессов и состояние после restart.
- Отдельный вердикт каждого этапа: PASS, FAIL, BLOCKED или NOT RUN.

Не сохранять credentials, cookies, raw ACP, чувствительные tool arguments/output или chain-of-thought. Оставлять только необходимое безопасное evidence. Диагностический доступ runner к состоянию не должен помогать агенту обходить неисправный продуктовый путь.

Общий PASS возможен только при успехе всех обязательных этапов выбранного и заранее зафиксированного профиля. Частичный smoke и полный real-harness прогон должны называться по-разному.

## Acceptance

- Установочный контракт и prerequisites определены; обычный пользователь получает готовые проверяемые бинарники, а не обязан знать внутреннюю структуру source checkout.
- Первый агент устанавливает Secretary в чистую VM исключительно по инструкции.
- Второй независимый агент проходит матрицу CLI на установленном продукте.
- Все обязательные harness adapters проходят реальные задачи и независимую проверку результатов без fallback.
- Одна команда связывает установку, CLI, harness installation, работу через клиент и restart/reconnect в один run с проверками каждого этапа.
- Ошибки инструкции, установки, harness authorization, client delivery и восстановления нельзя скрыть импровизацией агента или заменить заявлением модели о PASS.
- Сквозной прогон не требует ручной правки SQLite, обращения к скрытым credentials или ремонта source code на тестовой машине.
- Evidence воспроизводимо, привязано к конкретному релизу и не содержит секретов.
